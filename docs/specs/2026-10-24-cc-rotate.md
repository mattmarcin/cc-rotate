# cc-rotate: one Claude Code profile, a pool of accounts

Status: draft for review, 2026-10-24.
Tested against Claude Code 2.1.310 on Windows 11 (native install).

## 1. Goal

Run all Claude Code CLI work under a single profile so every session can see and message every other session, while a pool of Claude Max accounts backs that profile.
When the active account nears its 5-hour or weekly limit, the profile switches to another account in place, and running sessions continue on their next request with no restart and no proxy.
A local dashboard shows every account, its live and historical usage, and how rotation is spreading load, and it runs the official Claude login for any account that needs one.

## 2. Non-goals

- No HTTP proxy, no `ANTHROPIC_BASE_URL` override, no modification of the Claude Code binary.
- cc-rotate never calls Anthropic APIs itself: no token refresh, no usage polling.
  All Anthropic traffic is Claude Code's own.
- The Claude desktop app is out of scope.
  It injects its own token through environment variables and owns refresh, and Claude Code prefers an injected token over `.credentials.json`, so a file swap cannot reach it.
- macOS and Linux are out of scope for v1.
  The credential backend on macOS is the Keychain, not a file.
- Profiles the user already has (for example one `CLAUDE_CONFIG_DIR` per account) are not changed, except for the opt-in usage reporting in section 9.

## 3. What Claude Code already does (research findings)

These behaviors were read from the 2.1.310 bundle.
They are undocumented internals, so section 12 turns each one into an end-to-end acceptance test, and `cc-rotate-ctl doctor` warns on any untested Claude Code version.

| # | Behavior | Why it matters |
|---|---|---|
| F1 | Before using its token, each session stats `<profile>\.credentials.json`; if the mtime changed it drops the in-memory credential and re-reads the file. The 30 s figure is the read-cache TTL, which an mtime change bypasses. | A swap reaches every running session on its next API request. |
| F2 | On a credentials change, an "adopt sibling login" path re-runs account-dependent setup (managed settings, claude.ai connectors). | Claude Code itself expects another process to change the login under it. |
| F3 | Saving a refreshed token is compare-and-swap: it writes only if the on-disk `refreshToken` still equals the one it sent; otherwise it adopts the newer on-disk login. | A session still on account A never overwrites a swap to B. |
| F4 | Refresh runs under two lock directories with proper-lockfile semantics: `<profile>\.oauth_refresh.lock` and the legacy `<profile>.lock` (stale after 60000 ms, mtime updated every 5000 ms). After acquiring, it re-reads the file and refreshes whatever is on disk. | cc-rotate can exclude refreshes during a swap by holding the same locks. |
| F5 | The rate-limit tracker has an account epoch: on account change it clears utilization state and drops responses tagged with the previous epoch. | After a swap, the statusline stops reporting the old account's percentages. |
| F6 | Statusline input carries `rate_limits.five_hour` and `rate_limits.seven_day`, each with `used_percentage` and `resets_at` (epoch seconds). The statusline runs after every assistant message, and also every `refreshInterval` seconds (the setting is in seconds). | Usage samples and the swap trigger cost nothing extra. |
| F7 | The `StopFailure` hook receives `error` from a fixed set that includes `rate_limit`. | Backstop trigger when a turn stops at the limit. |
| F8 | When the account's login is rejected (`invalid_grant`), Claude Code blanks `refreshToken`, `accessToken` and `expiresAt` in the file. | Detects a dead login. |
| F9 | `claude auth login --claudeai [--email <e>]` runs without a TTY: it prints a sign-in URL, opens the browser, completes through a localhost callback, and also accepts a pasted code on stdin. `CLAUDE_CONFIG_DIR` points it at any directory. | The dashboard can run the official login flow and capture its result. |
| F10 | `.credentials.json` holds `claudeAiOauth` (the account login) and `mcpOAuth` (MCP server logins) side by side. | A swap must replace only `claudeAiOauth`. |
| F11 | On a quota 429 for the 5-hour or weekly window, the request does not fail: it sleeps until the reset and sends "usage limit recheck" probes with the current credentials; an admitted probe resends the request at once. Recheck cadence was not determined from the bundle. | A turn that hits the wall resumes on its own once a swap lands, and the turn may never stop, so `StopFailure` may not fire. |

Prior art (claude-account, clauth, claude-auth) swaps credential files between sessions, with no lock coordination with Claude Code's refresh and no live swap.
The claude-account README independently confirms the refresh-token rotation hazard that section 6 addresses.

## 4. Architecture

```
            ┌──────────────── profile  %USERPROFILE%\.claude-rotate ─────────────┐
 user  ──►  │ claude (session 1..n)        .credentials.json  (active login)     │
            │   statusLine ─► cc-rotate-ctl statusline ─┐                        │
            │   StopFailure ─► cc-rotate-ctl hook ──────┤                        │
            └───────────────────────────────────────────┼────────────────────────┘
                                                        ▼
                 ccr-core (Rust): store · lock · credfile · scheduler · login
                                                        ▲
            cc-rotate app (Tauri 2: window + tray) ─────┘   reads/writes the same store
            %LOCALAPPDATA%\cc-rotate\store.db  (SQLite, WAL)
```

A Rust Cargo workspace with three members:

- `crates/ccr-core`: the library every entry point uses.
- `crates/ccr-cli`: the `cc-rotate-ctl.exe` binary (statusline, hook, swap, login, status, doctor, setup).
- `app/src-tauri`: the `cc-rotate-app.exe` Tauri 2 desktop app (dashboard window, tray icon, native notifications), with its UI in `app/ui` (TypeScript, Vite, uPlot).

Rotation depends only on `cc-rotate-ctl.exe`, never on the app running.
The app is the only place native notifications come from, so it registers itself to start at login.

### 4.1 Components

- **store**: SQLite schema, migrations, and transactions over `rusqlite` with bundled SQLite.
- **lock**: acquires and releases Claude Code's two refresh locks with matching semantics, plus cc-rotate's own swap lock.
- **credfile**: reads and atomically writes `.credentials.json`, touching only `claudeAiOauth`.
- **scheduler**: decides whether to swap and to which account.
- **sampler**: turns statusline input into usage samples and keeps the store current (write-back).
- **login**: runs `claude auth login` in a staging directory and imports the result.
- **app**: Tauri commands over ccr-core, a 1 s poll of SQLite `PRAGMA data_version` that pushes a change event to the UI, the tray, and notifications.

### 4.2 Files and names

| Item | Value |
|---|---|
| Profile directory | `%USERPROFILE%\.claude-rotate` (override with `--profile`) |
| Launch alias | PowerShell function `cc-rotate` added to `$PROFILE` by `cc-rotate-ctl setup --install-alias`; it sets `CLAUDE_CONFIG_DIR` for the child `claude` process only |
| Control CLI | `cc-rotate-ctl.exe`, installed to `%USERPROFILE%\.local\bin` by default |
| Desktop app | `cc-rotate-app.exe`, installed next to the CLI |
| Store | `%LOCALAPPDATA%\cc-rotate\store.db` |
| Login staging | `%LOCALAPPDATA%\cc-rotate\staging\<uuid>\` |
| Logs | `%LOCALAPPDATA%\cc-rotate\logs\` |

### 4.3 Profile setup

`cc-rotate-ctl setup [--from <template profile>] [--profile <dir>] [--install-alias]` creates the rotation profile so a new user does not hand-edit anything.
The template defaults to `%USERPROFILE%\.claude`.

- Copies `settings.json`, `settings.local.json`, `keybindings.json`, and the `agents`, `commands`, `hooks`, `skills` and `plugins` directories when present, rewriting every occurrence of the template's path to the new profile's path in copied JSON (hook commands and plugin install paths reference their own profile).
- Links `CLAUDE.md` with a hard link when both profiles are on one volume, else copies it.
- In the new `settings.json`, records the template's `statusLine.command` as `statusline_downstream`, sets `statusLine` to `cc-rotate-ctl statusline` with `refreshInterval` 30 (seconds), and appends a `StopFailure` hook running `cc-rotate-ctl hook stop-failure`.
- Merges into `.claude.json` from the template: onboarding flags (so the first launch skips onboarding), user-level `mcpServers`, and per-project trust flags and MCP settings (`mcpServers`, `enabledMcpjsonServers`, `disabledMcpjsonServers`, `disabledMcpServers`).
  Values already in the profile always win, so re-running setup never undoes a change made there.
- Never copies `.credentials.json` (including MCP OAuth tokens, which each profile signs in to once with `/mcp`), the template's account data, history, project transcripts, or sessions.
- Refuses to overwrite an existing profile unless `--force` is given, and `--force` still keeps an existing `.credentials.json`.
- `--install-alias` appends a `cc-rotate` function to the PowerShell `$PROFILE` (idempotent, marked with a comment block).

## 5. Store

SQLite in WAL mode with `busy_timeout` 5000 ms, since many statusline processes write at once.

- `accounts(id, label, email, account_uuid UNIQUE, org_uuid, subscription_type, rate_limit_tier, state, priority, added_at, last_login_at, note)`
  - `state` is one of `active`, `parked`, `needs_login`, `paused`.
  - At most one row is `active`, enforced by a partial unique index; zero only when every account is `needs_login` or `paused`.
- `credentials(account_id PK, oauth_blob, refresh_fp, expires_at, refresh_expires_at, updated_at, source)`
  - `oauth_blob` is the `claudeAiOauth` object encrypted with Windows DPAPI (CurrentUser scope).
  - `refresh_fp` is a SHA-256 prefix of the refresh token, so comparisons never decrypt.
  - `source` is `login`, `swap_out` or `sync`.
- `samples(ts, account_id, profile, session_id, five_pct, five_resets_at, week_pct, week_resets_at)`, indexed on `(account_id, ts)`.
- `events(ts, kind, account_from, account_to, reason, detail_json)`, where `kind` is one of `swap`, `swap_skipped`, `login`, `sync`, `dead_login`, `pool_exhausted`, `error`.
- `settings(key, value)` holds the thresholds and options in section 13.

**Invariant:** the active account's newest login lives in `.credentials.json`; the store's copy of that row may lag.
Every parked account's newest login lives only in the store.
This is what makes the store the single source of truth for parked accounts without any process racing Claude Code for the active one.

## 6. Swap protocol

Triggers, in priority order:

1. The statusline sample for the active account reaches `five_hour >= swap_threshold_5h` or `seven_day >= swap_threshold_7d`.
2. A `StopFailure` hook with `error == "rate_limit"`.
   This is a backstop only: under F11 a turn at the wall usually sleeps instead of stopping, and trigger 1 still fires because the statusline reports 100%.
3. A dead login (F8) observed by the sampler.
4. A manual swap from the CLI or dashboard.

The statusline never performs a swap inline.
It spawns a detached `cc-rotate-ctl swap --from <account_id> --reason <r>` and returns, so the status line stays under its time budget.

Swap steps:

1. Acquire cc-rotate's swap lock (`%LOCALAPPDATA%\cc-rotate\swap.lock`, proper-lockfile semantics).
   If it is held, exit; another process is already swapping.
2. Re-read the store.
   If the active account is no longer `--from`, log `swap_skipped` and exit (idempotent across many sessions triggering at once).
   If the last swap was less than `swap_cooldown_s` ago and the trigger is a threshold, log `swap_skipped` and exit.
3. Pick the target account (section 7).
   If none is eligible, log `pool_exhausted` and exit without changing anything; the app turns that event into a notification.
4. Acquire `<profile>\.oauth_refresh.lock`, then `<profile>.lock`, in the same order and with the same stale and update settings as Claude Code (F4), timing out after 30 s.
   On timeout, release whatever was acquired, log `error`, and exit; the next trigger retries.
5. Under the locks, read `.credentials.json` and save its `claudeAiOauth` into the outgoing account's row (`source = swap_out`).
   If that block's refresh token is blank (F8), mark the outgoing account `needs_login` instead.
6. Decrypt the target's `claudeAiOauth`, write it into `.credentials.json` with every other key preserved, using write-to-temp then rename.
7. In one transaction, set outgoing to `parked` (or `needs_login`) and target to `active`, and log `swap` with the triggering sample.
8. Release the profile locks in reverse order, then the swap lock.

Mid-turn behavior: at 98% the active turn keeps running, and its next request goes out on the target account (F1).
If a request already hit the wall before the swap, the sleeping request resumes on the target account at its next recheck probe (F11).

Why this closes the race: any refresh either finishes before step 4, so step 5 captures the rotated token, or starts after step 8, re-reads the file under the lock (F4), and refreshes the target account.
No order leaves a retired refresh token in the store.

## 7. Scheduler

An account is eligible when its state is `parked` and its effective usage is below both thresholds.
Effective usage per window is the last sampled percentage, or 0 when that window's `resets_at` is in the past.
An account with no samples is treated as 0.

Ranking among eligible accounts:

1. Lowest effective weekly percentage, so weekly budget drains evenly across the pool.
2. Then lowest effective 5-hour percentage.
3. Then `priority`, then `label`.

Parked accounts have no live samples, which is fine: their last sample plus `resets_at` gives an exact lower bound, and the store never needs to poll Anthropic.
Usage reported by the legacy profiles (section 9) feeds the same numbers, so an account busy in another profile is not chosen blindly.

## 8. Write-back and the statusline

The profile's `statusLine.command` is `cc-rotate-ctl statusline`, with `refreshInterval` 30 (seconds); it also runs after every assistant message. The desktop app runs the write-back step (step 3) every 5 s as well, so the store stays current when only non-interactive sessions run.
Each tick:

1. Parse stdin JSON.
2. If `rate_limits` is present, insert a sample for the active account.
   Discard it if either window's `resets_at` equals the most recent outgoing account's recorded `resets_at` within 120 s of a swap, as a guard on F5.
3. If `.credentials.json` mtime is newer than the last sync, read it; if its refresh token fingerprint differs from the active row's, store it (`source = sync`).
   This keeps the store at most one tick behind Claude Code's own refreshes.
4. Evaluate triggers 1 and 3 and spawn a detached swap if needed.
5. Forward the original stdin to the `statusline_downstream` command (if set) and print its output, prefixed with the active account label.

Budget: one `cc-rotate-ctl statusline` run without a downstream command (process start plus steps 1 to 4) completes in under 30 ms at the 95th percentile; the downstream command's own run time is added on top and is outside cc-rotate's control.

## 9. Usage reporting from the legacy profiles (opt-in)

The legacy profiles can run `cc-rotate-ctl statusline --observe` in front of their existing statusline.
Observe mode only records samples, attributed by `oauthAccount.accountUuid` from that profile's `.claude.json`, and tags them with the profile name.
It never touches credentials or triggers swaps.
This lets the dashboard show every account during a migration, and lets the scheduler avoid accounts the legacy profiles are draining.

## 10. Login flow

Used both for adding an account and for re-logging an account in `needs_login`.

1. Create `%LOCALAPPDATA%\cc-rotate\staging\<uuid>\`.
2. Spawn `claude auth login --claudeai --email <email>` with `CLAUDE_CONFIG_DIR` set to the staging directory, piping stdin, stdout and stderr.
   `--email` is omitted when adding a new account with no known email.
3. Parse the sign-in URL from stdout and show it, plus a paste-code field that writes to the child's stdin (F9).
   Claude Code opens the browser itself.
4. On exit code 0, read the staging `.credentials.json` `claudeAiOauth` and the staging `.claude.json` `oauthAccount`.
5. For a re-login, refuse the import if `accountUuid` differs from the target account, and tell the user which email actually signed in.
6. Upsert the account and its credentials (`source = login`).
   A re-logged account goes to `parked`, or to `active` if the pool had no active account.
7. Delete the staging directory, including on failure, cancel, and the 10-minute timeout.

Rules:

- Every account in the pool gets its own fresh login.
  Tokens are never copied from the legacy profiles, because a shared refresh token would break whichever holder refreshes second.
- The browser signs in as whatever claude.ai account it is currently logged into.
  The UI states the expected email before opening and suggests a separate browser profile per account when the wrong one keeps signing in.

## 11. Dashboard app

`cc-rotate-app.exe` is a Tauri 2 window plus a tray icon; closing the window hides it to the tray, and `cc-rotate-ctl dashboard` launches or focuses it.
It is single-instance, starts at login (toggle in the app), and exposes no network port: the UI talks to the Rust side only through Tauri commands and events.
The tray tooltip shows the active account and its 5-hour and weekly percentages; the tray menu offers Open, Swap now, and Quit.
Native notifications fire for `pool_exhausted`, `dead_login`, and any account entering `needs_login`.
The UI is TypeScript built with Vite, with uPlot for charts.
Light and dark themes follow the system.
UI copy uses no em dashes.

Views:

- **Pool header:** active account, pool headroom (summed weekly percentage remaining over eligible accounts), next reset, swaps in the last 24 hours, and a warning banner for `pool_exhausted` or any `needs_login`.
- **Accounts:** one row per account with label, email, plan, state badge, 5-hour and weekly meters with reset countdowns, last-sample age, and login expiry.
  Row actions: Make active, Pause or Resume, Re-login, Remove.
- **Usage over time:** weekly percentage per account as lines over 7 days, a 5-hour percentage strip per account over 24 hours, and swap events as vertical markers labelled with the reason.
- **Events:** filterable log of swaps, skips, logins, syncs and errors.
- **Login:** the section 10 flow in a dialog with live status (waiting for browser, received, imported, failed).
- **Health:** `doctor` results (section 12), Claude Code version, and the store path.

## 12. Errors, health and version safety

- Every failure path logs an `events` row and leaves `.credentials.json` either untouched or fully written, never partial.
- `cc-rotate-ctl doctor` checks:
  - the Claude Code version against the tested list,
  - that both lock paths resolve as expected,
  - that the profile's `statusLine` and `StopFailure` hook point at cc-rotate,
  - that exactly one account is active, or that zero are and every account is `needs_login` or `paused`,
  - that `.credentials.json` matches the active account's `account_uuid` by fingerprint,
  - that DPAPI decrypt works for every row.
- On an untested Claude Code version, rotation still runs, the dashboard shows a warning, and the next manual verification uses the E2E suite below.
- Back up `.credentials.json` before the first swap of each day to `%LOCALAPPDATA%\cc-rotate\backups\`, keeping 7.

| `swap_cooldown_s` | 120 |

## 14. Requirements

1. R1: A swap changes the account used by every running CLI session in the profile on that session's next API request, with no restart.
2. R2: No interleaving of a Claude Code token refresh and a swap leaves any account's stored refresh token retired.
3. R3: A swap writes only `claudeAiOauth`; `mcpOAuth` and every other key in `.credentials.json` parse to the same values before and after.
4. R4: Concurrent triggers from many sessions produce at most one swap per `--from` account.
5. R5: No automatic swap happens within `swap_cooldown_s` of the previous swap, except for `StopFailure` or a dead login.
6. R6: When no account is eligible, nothing changes, and the dashboard shows a banner and (while the app runs) a native notification.
7. R7: The store never holds plaintext tokens on disk.
8. R8: cc-rotate makes no network requests to Anthropic.
9. R9: The statusline path meets the section 8 latency budget.
10. R10: The login flow imports a working login without the user opening a terminal, and rejects a re-login that signed in as a different account.
11. R11: The legacy profiles' credentials are never read for import or written.
12. R12: Every swap, skip, login, sync and error is visible in the dashboard events view within 2 s.

## 15. Testing

Unit tests (`cargo test`): scheduler ranking and eligibility, effective-usage reset math, credfile merge preserving unknown keys, store invariants, DPAPI round-trip, and lock interop against a real proper-lockfile holder in a child process.

End-to-end tests against the real `claude.exe` in a throwaway profile, with two real accounts (the user logs in once per account at the start):

- E1 (R1): start a session, swap A to B, send a prompt; `claude auth status --json` in the profile and the statusline's `resets_at` both reflect B.
- E2 (R2): set A's `expiresAt` in the file to the past so the next request refreshes, then fire a swap while that request is in flight; swap back to A and complete a request successfully.
- E3: park A until its access token expires, swap back, and confirm Claude Code refreshes from the stored refresh token.
- E4 (R4): ten sessions over threshold at once produce exactly one `swap` event.
- E5 (R10): add and re-login an account from the dashboard, including the wrong-account rejection.
- E6 (R11): run `claude auth status` in each legacy profile before and after the suite; results are unchanged.
- E7 (F5 guard): after a swap, no sample is attributed to B with A's `resets_at`.
- E8 (F11): with one account genuinely at its limit and swaps paused, start a turn so it sleeps at the wall, then resume swaps; the turn continues on the target account without user input.
  Record the time from swap to resumed response as the measured recheck latency, and if it exceeds 5 minutes, add a mitigation to this spec before release.
- `StopFailure` is verified with a recorded hook payload, since a real limit cannot be produced on demand.

## 16. Build order

1. Core library with store, lock, credfile and scheduler, plus unit tests.
2. CLI (`add`/`login`, `status`, `swap`, `pause`, `remove`, `doctor`) and the profile with its statusline and hook, then E1 to E4, E6 and E7.
3. Dashboard with the login flow, then E5.
4. Observe mode for the legacy profiles.

## 17. Decisions

1. Both swap thresholds default to 98%.
2. Every account joins the pool through a fresh login made inside cc-rotate (section 10).
   E2E tests E1 to E7 need two logged-in accounts; E8 needs one account genuinely at its limit.
3. There is no reserve concept in v1: every `parked` account is eligible, and `paused` is how a user holds one back.
4. The project is open source under the MIT license; no code or doc may assume a particular user, path, or account count.
5. Windows is the supported platform for v1; platform-specific code (DPAPI, process flags, PowerShell alias) sits behind `cfg(windows)` so Linux support can be added later.
