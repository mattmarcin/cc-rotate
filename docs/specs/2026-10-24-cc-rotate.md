# cc-rotate: one Claude Code profile, a pool of accounts

Status: draft for review, 2026-10-24.
Tested against Claude Code 2.1.310 on Windows 11 (native install).
Linux behavior was read from the 2.1.310 linux-x64 build and runs the Windows code paths unchanged; verified with real accounts in WSL.
macOS behavior was read from the 2.1.310 darwin-arm64 build (section 18) and verified with real accounts on a Mac: swaps through the Keychain in a desktop session, a renewal during a usage check, and identifying a changed login.
Over SSH the login Keychain is locked to the session, and Claude Code there neither reads a login in it nor saves one (section 18.1), so cc-rotate refuses to run Claude Code or swap there.

## 1. Goal

Run all Claude Code CLI work under a single profile so every session can see and message every other session, while a pool of the user's own Claude subscription accounts backs that profile.
When the active account nears any of its usage limits, the profile switches to another account in place, and running sessions continue on their next request with no restart and no proxy.
Accounts are used in an order the user sets, accounts without a weekly limit first, and rotation switches back to an account without a weekly limit once one is usable again.
A local dashboard shows every account, its live and historical usage, and how rotation is spreading load, and it runs the official Claude login for any account that needs one.

## 2. Non-goals

- No HTTP proxy, no `ANTHROPIC_BASE_URL` override, no modification of the Claude Code binary.
- cc-rotate never calls Anthropic APIs itself: no token refresh, no usage requests of its own.
  All Anthropic traffic is Claude Code's own; a usage check (section 20) runs Claude Code's `/usage`, and a login renewed during one was renewed by Claude Code.
  The one prompt the user did not type is a warm-up (section 23), which the user turns on per account.
- The Claude desktop app is out of scope.
  It injects its own token through environment variables and owns refresh, and Claude Code prefers an injected token over `.credentials.json`, so a file swap cannot reach it.
- Profiles the user already has (for example one `CLAUDE_CONFIG_DIR` per account) are not changed, except for the opt-in usage reporting in section 9.
- Cloud work (cloud agents, `/ultrareview`, routines, Claude Code on the web) and Remote Control are out of scope.
  They run on, or are pinned to, the account that started them, while the local session reaches them with whatever login the profile holds now (F18, F19).
  cc-rotate does not hold swaps for them; the README's "What it does not cover" documents the effects.

## 3. What Claude Code already does (research findings)

These behaviors were read from the 2.1.310 bundle.
They are undocumented internals, so section 12 turns each one into an end-to-end acceptance test, and `cc-rotate-ctl doctor` warns on any untested Claude Code version.

| F8 | When the account's login is rejected (`invalid_grant`), Claude Code blanks `refreshToken`, `accessToken` and `expiresAt` in the file. | Detects a dead login. |

The statusline's `rate_limits` exposes `five_hour` and `seven_day` (plus `spend_limit` behind a gateway), and the input carries `model.id`. `/usage` groups its `limits[]` rows by kind: `session`, `weekly_all`, `weekly_scoped` (with a model scope). | cc-rotate records every window the statusline reports, by name, so a window Claude Code adds later needs no code change; model-scoped windows apply by `model.id`. |

Token renewals also merge the new account's profile fields (`seatTier`) into the old `oauthAccount`. | cc-rotate does not use the rotation profile's `cachedUsageUtilization` or `oauthAccount` for usage or plans: neither can be attributed to an account reliably. |
| F16 | In a profile whose login never changes account, the `cachedUsageUtilization` stamp is reliable: Claude Code writes the cache only when the profile's `oauthAccount.accountUuid` is still the one it read before the fetch, and drops a cache stamped with another account when it reads it. The cache is `{fetchedAtMs, accountUuid, utilization}`, where `utilization` is the `GET /api/oauth/usage` body: one field per limit system (`five_hour`, `seven_day`, `seven_day_opus`, many codenamed ones, mostly null) and `limits[]`, the rows `/usage` shows (`kind`, `percent`, `resets_at` as RFC 3339, optional `scope.model` or `scope.surface`). Sessions refresh it when they read usage, for example for `/usage` and at a limit (observed: a profile with an agent at its 5-hour limit held a reading 6 minutes old). | The user's other profiles tell cc-rotate when an account was used up outside the pool (section 9.1). |
| F15 | Every login (`claudeAiOauth`) carries `subscriptionType` (`max`, `team`, `pro`, `enterprise`) and `rateLimitTier` (`default_claude_max_5x`, ...), and renewals repeat them. Claude Code treats `team` with `default_claude_max_5x` as a premium Team seat. | Plans ("Max 5x", "Team 5x") are derived from the login itself, which travels with the account. |
| F17 | `/usage` runs without a session (`claude -p /usage`, `supportsNonInteractive`): zero turns, zero tokens. With a claude.ai login holding the `user:profile` scope it fetches `GET /api/oauth/usage` (renewing the login first when its access token expired, `refreshOAuth: true`) and caches the body in the profile's `.claude.json` (F16); a login injected with `CLAUDE_CODE_OAUTH_TOKEN` is treated as an API token and fetches nothing. The endpoint is rate limited per login: a 429 carries `retry-after`, which Claude Code holds in memory (capped at 1 h, 5 min without the header) and logs as `429 remembered for this bearer; not asking again for <n>s`. A run takes about 2 to 4 s. | cc-rotate reads accounts that are not in use with Claude Code's own request and no quota (section 20). |
| F11 | On a quota 429 for the 5-hour or weekly window the turn stops ("You've hit your session limit") and `StopFailure` fires. Only with `CLAUDE_CODE_RETRY_WATCHDOG=1` does the request sleep instead, and with `CLAUDE_CODE_RETRY_WATCHDOG_USAGE_LIMIT_RECHECK_MS` also send "usage limit recheck" probes; a probe reads the current login, but the request resent after an admitted probe keeps the client, and so the login, it was built with (only cloud sessions rebuild it). Verified end to end against a fake API (section 21). | A swap never reaches a turn that stopped at a limit, nor a request sleeping under the watchdog: cc-rotate wakes the session instead (section 21), and `doctor` warns about the watchdog. |
| F18 | Cloud work started from a local session (Agent `isolation: "remote"`, cloud workflow runs, `/ultrareview`, ultraplan, autofix) is a `remote_agent` task. The session polls `GET /v1/code/sessions/<id>/events` every second with only the profile's current bearer token; a failed poll is logged and retried indefinitely, except that a review gives up after 5 consecutive 404s. Each pending task has `<profile>/projects/<project>/<session>/remote-agents/remote-agent-<taskId>.meta.json` (no account recorded), removed when the task ends; on resume, a 404 for its session id deletes the file and any other error skips it for that run. A launch sends the current token with the organization from `CLAUDE_CODE_ORGANIZATION_UUID`, else `.claude.json` `oauthAccount.organizationUuid`, which a swap does not update (F14). Not determined: whether the server answers 404 or 403 for another account's session. | After a swap, results of cloud work started on another account arrive only once that account is active again, a resume under another account can drop them, and a launch after a swap across organizations names the wrong organization. Out of scope (section 2); the README says so. |
| F20 | Interactive sessions continue a task on their own after a usage limit resets (`autoContinueAtUsageLimit`, on by default, read from user settings): armed for the reset time plus 1 to 5 minutes, only when the reset is at most 6 hours away, at most twice in a row. Its message says "Continue the task you were working on when the limit was reached; do not repeat work that is already complete." It stays armed after another turn ran, and a credentials change from another process does not cancel it (only an in-session `/login` of another account does). | After cc-rotate wakes a session, Claude Code's own continue still arrives at the old account's reset; its wording makes it harmless, and cc-rotate's message mirrors it. |
| F21 | A command hook with `asyncRewake: true` runs in the background; when it exits with code 2, Claude Code wakes the session at once, even when idle, with the hook's stderr as a system reminder and "Stop hook feedback" shown to the user. Claude Code enforces its `timeout` (no upper bound) and kills it at teardown in `-p` mode. When Claude Code is killed, the hook keeps running: the shell between them waits for it. | The `StopFailure` hook can wait for a swap and wake the session, and has to notice by itself that its session is gone. |
| F22 | `claudeAiOauth.refreshTokenExpiresAt` is set from `refresh_token_expires_in` on every renewal, and stays the same date across renewals: a sign-in lasts a fixed time (about 30 days observed), however the account is used. | Renewing cannot keep an account signed in, so cc-rotate warns before a sign-in ends (section 21). |
| F23 | The status line input carries `version`, the running Claude Code's version. | cc-rotate learns which Claude Code its sessions run without starting it. |
| F19 | Remote Control pins the account that started it: when the bearer token changes it asks the server whose token it is, and for another account it ends Remote Control and archives the session ("signed-in claude.ai account or organization changed on this machine"). | The first swap after `/remote-control` ends it. Out of scope (section 2); the README says so. |
| F24 | The status line's `rate_limits` come from the process's rate-limit tracker, which only API responses update (a refusal at a usage limit too, through its headers); it is cleared when the session notices a new login, at its next request (F1, F5). Between responses the status line repeats the same numbers, minus any window whose reset has passed, however long the session idles (observed: a session idle for over two hours after a swap kept showing the account it used before). `cost.total_api_duration_ms` grows only with successful responses. | A session whose numbers have not changed since a swap has had no response since, so they are the account it used before (section 8). With several sessions on one account, the latest reading is often an older one, so an account's usage is each window's highest reading (section 7). |

Prior art (claude-account, clauth, claude-auth) swaps credential files between sessions, with no lock coordination with Claude Code's refresh and no live swap.
The claude-account README independently confirms the refresh-token rotation hazard that section 6 addresses.

## 4. Architecture

```
            ┌──────────────── profile  ~/.claude-rotate ─────────────────────────┐
 user  ──►  │ claude (session 1..n)        .credentials.json  (active login)     │
            │   statusLine ─► cc-rotate-ctl statusline ─┐                        │
            │   StopFailure ─► cc-rotate-ctl hook ──────┤                        │
            └───────────────────────────────────────────┼────────────────────────┘
                                                        ▼
                 ccr-core (Rust): store · lock · credfile · scheduler · login
                                                        ▲
            cc-rotate app (Tauri 2: window + tray) ─────┘   reads/writes the same store
            <data dir>/store.db  (SQLite, WAL)
```

A Rust Cargo workspace with three members:

- `crates/ccr-core`: the library every entry point uses.
- `crates/ccr-cli`: the `cc-rotate-ctl` binary (statusline, hook, swap, login, status, watch, report, doctor, setup) and the `cc-rotate` launcher.
- `app/src-tauri`: the `cc-rotate-app` Tauri 2 desktop app (dashboard window, tray icon, native notifications), with its UI in `app/src` (TypeScript, Vite, charts drawn as SVG).

Rotation depends only on `cc-rotate-ctl`, never on the app running.
The app is the only place native notifications come from, so it registers itself to start at login.

### 4.1 Components

- **store**: SQLite schema, migrations, and transactions over `rusqlite` with bundled SQLite.
- **lock**: acquires and releases Claude Code's two refresh locks with matching semantics, plus cc-rotate's own swap lock.
- **credfile**: reads and atomically writes `.credentials.json`, touching only `claudeAiOauth`.
- **scheduler**: decides whether to swap and to which account.
- **sampler**: turns statusline input into usage samples and keeps the store current (write-back).
- **login**: runs `claude auth login` in a staging directory and imports the result.
- **app**: Tauri commands over ccr-core, a 1 s poll of SQLite `PRAGMA data_version` that pushes a change event to the UI, the tray, and notifications.

### 4.2 Files and names

| Item | Value |
|---|---|
| Profile directory | `~/.claude-rotate` (override with `--profile`) |
| Launcher | `cc-rotate`, an executable next to the CLI (section 4.4) |
| Control CLI | `cc-rotate-ctl`, installed to `~/.local/bin` by default |
| Desktop app | `cc-rotate-app`, installed next to the CLI |
| Data dir | `%LOCALAPPDATA%\cc-rotate` on Windows, `~/.local/share/cc-rotate` on Linux, `~/Library/Application Support/cc-rotate` on macOS (override with `CC_ROTATE_DATA_DIR`) |
| Store | `<data dir>/store.db`, with its key in `<data dir>/master.key` |
| Login staging | `<data dir>/staging/login-<uuid>/` |
| Usage check scratch profiles | `<data dir>/staging/check-<account id>-<start ms>-<uuid>/` |
| Account locks | `<data dir>/locks/account-<id>.lock` |
| Logs | `<data dir>/logs/` |

### 4.3 Profile setup

`cc-rotate-ctl setup [--from <template profile>] [--profile <dir>] [--remove-alias] [--keep-existing]` creates the rotation profile so a new user does not hand-edit anything.
The template defaults to `~/.claude`.

- Copies `settings.json`, `settings.local.json`, `keybindings.json`, and the `agents`, `commands`, `hooks`, `skills` and `plugins` directories when present, rewriting every occurrence of the template's path to the new profile's path in copied JSON (hook commands and plugin install paths reference their own profile).
- Links `CLAUDE.md` with a hard link when both profiles are on one volume, else copies it.
- In the new `settings.json`, records the template's `statusLine.command` as `statusline_downstream`, sets `statusLine` to `cc-rotate-ctl statusline` with `refreshInterval` 30 (seconds), and appends a `StopFailure` hook running `cc-rotate-ctl hook stop-failure` for `rate_limit`, in the background (`asyncRewake`) with a 24-hour timeout (section 21).
- Appends a `SessionStart` hook running `cc-rotate-ctl hook session-start` for herdr (section 19).
  For each hook event it first drops only the groups that run `cc-rotate-ctl`, so the user's own hooks and herdr's stay, and `--force` never duplicates cc-rotate's.
- Merges into `.claude.json` from the template: onboarding flags (so the first launch skips onboarding), user-level `mcpServers`, and per-project trust flags and MCP settings (`mcpServers`, `enabledMcpjsonServers`, `disabledMcpjsonServers`, `disabledMcpServers`).
  Values already in the profile always win, so re-running setup never undoes a change made there.
- Never copies `.credentials.json` (including MCP OAuth tokens, which each profile signs in to once with `/mcp`), the template's account data, history, project transcripts, or sessions.
- Refuses to overwrite an existing profile unless `--force` is given, and `--force` still keeps an existing `.credentials.json`.
  With `--keep-existing` it keeps an existing profile and succeeds instead, only bringing cc-rotate's own hook groups in its `settings.json` up to this release's (the same replacement as above), so the installer runs setup on every upgrade and setup itself decides from the profile it resolves (the `profile_dir` setting is unset for the default profile, or when the store was created after the profile).
- The statusline and hook commands start with the `cc-rotate-ctl` path unquoted.
  On Windows, Claude Code may run them through PowerShell, cmd or Git Bash, and a quoted path followed by arguments is a PowerShell parse error, so a path with spaces uses its 8.3 short form.
  On Unix they run through a POSIX shell, so a path with spaces or other special characters is single-quoted.
- `--remove-alias` removes the `cc-rotate` PowerShell function (the block between `# >>> cc-rotate >>>` and `# <<< cc-rotate <<<`) that earlier versions added, because a PowerShell function hides an executable of the same name.
  With an existing profile and no `--force`, that is all setup does; `doctor` warns while the function is still there.

### 4.4 Launcher

`cc-rotate [args]` resolves the profile like every other entry point (`--profile` is not taken, since every argument goes to Claude Code; `CC_ROTATE_PROFILE`, then the `profile_dir` setting, then `~/.claude-rotate`), finds `claude` (see below), sets `CLAUDE_CONFIG_DIR` for the child only, and passes every argument through.
It is an executable rather than a shell function so it works the same in every shell, including tools that restore a session by typing `cc-rotate --resume <id>` into a fresh shell.

- On Unix it replaces itself with `claude` (`exec`), so signals and the exit code are Claude Code's own.
- On Windows it waits for `claude` and exits with its exit code.
  It registers a console control handler that ignores Ctrl+C and Ctrl+Break, so those reach Claude Code while the launcher keeps waiting; a handler, unlike the ignore flag, is not inherited by the child.
- It warns on stderr when started in the home folder, where Claude Code does not run status lines, then continues.
- On macOS, in a session that cannot use the login Keychain (section 18.1), it refuses to start Claude Code and says why, unless the arguments need no login (`--version`, `--help`, `update`, `doctor`, `mcp`, `config`, `install`); it asks `security` for at most 3 s, since a locked Keychain in a desktop session shows a dialog instead.

Every entry point finds `claude` the same way.
The `claude_path` setting comes first and must be a full path.
Then the absolute folders on `PATH`: a relative entry would resolve against wherever cc-rotate runs, such as a project folder.
Then, since an app macOS starts at login gets only `/usr/bin:/bin:/usr/sbin:/sbin`, the folders installers use: `~/.local/bin` (Claude Code's native installer), then on Unix `/opt/homebrew/bin`, `/usr/local/bin` and `/home/linuxbrew/.linuxbrew/bin`, and on Windows npm's `%APPDATA%\npm`.
On Unix a `claude` found in one of those is used only when every step to it is the user's: the path is walked one part at a time from `/`, following each link where it leads, as the system resolves it.
Every link must belong to root or the user, and so must every folder and the program, whose permissions must let no one else change them.
That means not writable by everyone (unless a sticky folder like `/tmp`, where others can't rename or remove what isn't theirs), nor by a group other than macOS's `admin` or the user's private one: named after them with no members listed, as Debian, Ubuntu and Fedora make them, whose umask 002 leaves `~/.local` group-writable.
The private group counts only on a file or folder without a POSIX access control list (Linux), whose group bits would be the list's limit rather than the group's.
Another account whose own primary group is the user's private group isn't listed as a member, so it isn't seen.
A shared Homebrew prefix may belong to another user.
macOS access control lists are not read.
A `claude` refused this way is reported by the error and by doctor with the step that failed, and setting `claude_path` to it uses it anyway; a refused herdr is reported by doctor.
Claude Code runs with its own folder added to the end of `PATH` when `PATH` is set and lacks it, so a `claude` installed with Homebrew's npm finds the `node` beside it; being last, the folder shadows nothing in the session.
herdr is found the same way, without `claude_path`.

## 5. Store

SQLite in WAL mode with `busy_timeout` 5000 ms, since many statusline processes write at once.

- `accounts(id, label, email, account_uuid UNIQUE, org_uuid, subscription_type, rate_limit_tier, state, position, weekly_limit, added_at, last_login_at, note)`
  - `state` is one of `active`, `parked`, `needs_login`, `paused`.
  - `position` is the user's order (lower is used first); a new account goes to the end, and reordering numbers every account from 1.
  - `weekly_limit` is `auto` (detect it, section 7), `yes` or `no`.
  - `subscription_type` and `rate_limit_tier` are refreshed from every stored login (F15).
  - At most one row is `active`, enforced by a partial unique index; zero only when every account is `needs_login` or `paused`.
- `credentials(account_id PK, oauth_blob, refresh_fp, expires_at, refresh_expires_at, updated_at, source)`
  - `oauth_blob` is the `claudeAiOauth` object sealed as described in section 5.1.
  - `refresh_fp` is a SHA-256 prefix of the refresh token, so comparisons never decrypt.
  - `source` is `login`, `swap_out` or `sync`.
- `samples(id, ts, account_id, profile, session_id, model)`, indexed on `(account_id, ts)`: one reading, with the session's model when the statusline reported one.
- `sample_windows(sample_id, account_id, name, pct, resets_at, high)`, primary key `(sample_id, name)`, indexed on `(account_id, name, resets_at)`: every usage window of a reading, named as Claude Code names it (`five_hour`, `seven_day`, ...), with `high` the window's usage as of that reading (section 7.1), worked out when the reading is recorded from the latest recorded row of the same window.
  A window the data source did not report has no row; it is never stored as 0%.
- `session_processes(session_id, key, started_ms, seen_ms)`, primary key `(session_id, key)`: each session's Claude Code processes, told apart by when each started.
  The status line gives how long its process has run (`cost.total_duration_ms`, restored with the cost on `--resume`), so `now - total_duration_ms` is the process's start plus however long the status line took to start, never earlier.
  A known process whose earliest such reckoning (`started_ms`) is within 20 s of this one is that one (an earlier reckoning becomes its `started_ms`; the first may have been the slow one), anything else a new one; its `key`, its first reckoning, is what `session_costs` and `session_readings` use.
  A resumed process restores the run time it had, so it never reckons earlier than the one it was resumed from, but one resumed within 20 s of it, while it still runs, shares its key.
  The status line's parent process cannot tell it: it runs under a process of its own each time, gone by the time it is asked (observed on Windows, where Git Bash runs it).
  A session whose status line does not give the run time shares one key with its session.
- `session_readings(session_id, process, windows, since_ms, seen_ms)`, primary key `(session_id, process)`: the usage windows each session's Claude Code process last reported on the status line, and since when unchanged (section 8, step 2).
- `events(ts, kind, account_from, account_to, reason, detail_json)`, where `kind` is one of `swap`, `swap_skipped`, `login`, `sync`, `dead_login`, `pool_exhausted`, `error`.
- `settings(key, value)` holds the thresholds and options in section 13.

### 5.1 Encryption at rest

Every sealed blob is `CCR2 || nonce (24 bytes) || XChaCha20-Poly1305 ciphertext and tag`, under one random 256-bit data key with a fresh random nonce per blob.
The associated data binds a blob to its purpose: `cc-rotate/credential/v2/account:<id>` for a login, `cc-rotate/backup/v2` for a backup, so a blob moved to another row or file fails to open.

The key is `<data dir>/master.key`, 32 raw bytes, created on first use.
It is written in full to a temporary file and published with a hard link, which fails rather than replacing an existing file, so concurrent first uses agree on one key.
On Unix the file is mode 0600 and the data directory 0700; on Windows it inherits the user profile's ACL (the user, SYSTEM, Administrators).
When the key file is missing but sealed logins exist, cc-rotate reports it instead of creating a new key.

The key must be readable without any prompt: the statusline is a short-lived process that runs every few seconds per session, often headless or over SSH.
That rules out OS keyrings as the default (a locked Secret Service over SSH, Keychain access prompts for unsigned binaries whose signature changes on every build).
The key file protects against casual reads and against a copy of the store leaking on its own.
It does not protect against code running as the same user, which is the same trust level as Claude Code's own plaintext `.credentials.json`.

Schema 1 stores sealed logins with Windows DPAPI.
Opening a schema 1 store on Windows decrypts each login with DPAPI and re-seals it in the format above in the same transaction that sets `user_version` to 2, and converts the `.dpapi` backups to `.ccr`.
A login that cannot be converted is left in place, logged as an `error` event, and reading it asks for a new sign-in.
DPAPI code remains only for that conversion.

Schema 3 replaces the two fixed usage columns with `sample_windows`, in the transaction that sets `user_version` to 3.
Every sample keeps its id, and its `five_pct`/`week_pct` columns become `five_hour`/`seven_day` rows when not null.
`priority` is renamed to `position` with its values kept, so accounts that shared a priority share a place in the order until the user reorders them.

Schema 10 adds `sample_windows.high` and works it out for every recorded window, replaying the readings in the order they were recorded, in the transaction that sets `user_version` to 10.

**Invariant:** the active account's newest login lives in `.credentials.json`; the store's copy of that row may lag.
Every parked account's newest login lives only in the store.
This is what makes the store the single source of truth for parked accounts without any process racing Claude Code for the active one.

## 6. Swap protocol

Triggers, in priority order:

1. A window of the active account's usage (section 7) that applies to the model in use reaches its threshold.
2. A `StopFailure` hook with `error == "rate_limit"`, once the status line recorded the reading of the stop (section 21).
   The swap does not reach the stopped turn (F11); the hook wakes the session afterwards.
3. A dead login (F8) observed by the sampler.
4. A manual swap from the CLI or dashboard.
5. Switch back: while an account that may have a weekly limit is in use, an account without one is usable again (section 7.2).

The statusline never performs a swap inline.
It spawns a detached `cc-rotate-ctl swap --from <account_id> --reason <r>` and returns, so the status line stays under its time budget.

Swap steps:

1. Acquire cc-rotate's swap lock (`<data dir>/swap.lock`, proper-lockfile semantics).
   If it is held, exit; another process is already swapping.
2. Re-read the store.
   If the active account is no longer `--from`, log `swap_skipped` and exit (idempotent across many sessions triggering at once).
   If the last swap was less than `swap_cooldown_s` ago and the trigger is a threshold or a switch back, log `swap_skipped` and exit, unless the trigger is a threshold and the active account arrived over its limit (section 7.2).
   For a switch back, also skip when `switch_back_target` finds no account any more.
3. Record the readings the user's other profiles hold (section 9.1), then pick the target account (section 7).
   When the pick's latest reading is older than `usage_check_max_age_s` and checks are on, check it first (section 20) and pick again; at most three checks per swap, none started after 25 s.
   Then take the target's account lock (section 20), waiting for a background check of it to finish, recover what a dead check left (section 20.3), and pick again under the lock if a check that finished meanwhile found the target over a threshold, rejected or held back; an account whose lock or leftovers keep it busy is passed over.
   Before all this, a threshold swap whose reading may not be the account in use's own confirms it first (section 20.4), and is skipped when the account's own reading is below its thresholds.
   If none is eligible, log `pool_exhausted` and exit without changing anything; the app turns that event into a notification. When the only eligible accounts were passed over as busy (a check of them running), the swap is skipped instead: the pool is not exhausted.
4. Acquire `<profile>/.oauth_refresh.lock`, then `<profile>.lock`, in the same order and with the same stale and update settings as Claude Code (F4), then `<profile>/.storage-write.lock` (F12), timing out after 30 s.
   On timeout, release whatever was acquired, log `error`, and exit; the next trigger retries.
   Read everything else the commit needs, then record the swap as pending (`swap_pending` in `meta`: the target login's fingerprint, the outgoing and the target account) before writing; the status line's write-back leaves a file with that fingerprint alone, so a tick before the commit cannot store the target's login as the outgoing account's. The commit clears it, and a failed commit restores the outgoing login and clears it.
   A failed write or commit restores the outgoing login and clears the mark only when the profile verifiably has the outgoing login again; otherwise the mark stays.
   A swap that died in between (a crash, or a failure that could not be undone) leaves the mark with nobody holding the swap lock, and is settled only on certainty (`swap::finish_dead_swap`): when the profile has exactly the outgoing account's login, the write never happened and the mark is cleared; when it has exactly the target's, the swap is completed (states only; the outgoing login was stored before the write); when it verifiably has no usable login (Anthropic rejected whichever it was, or a `/logout`; on macOS only while the Keychain can be read, since a locked Keychain can hide the live login behind a stale or missing file), the outgoing account's stored login, saved before the write, is put back under Claude Code's locks and the target is held back until a check settles whether its login still works (20.3); otherwise (a renewal since, a `/login`) Claude Code is asked whose login it is, with a copy whose refresh token is removed, matching the account id or else the email, and the organization where both are known, and the swap is completed, forgotten, or the login treated as foreign accordingly.
   Until then nothing is stored from the profile, no usage check runs, a fresh login of the active account is stored but not written into the profile, and no swap runs, not even one asked for by hand: each would overwrite the only copy of a login nobody can identify, or file it under the wrong account. The sessions go on with the login the profile has. Settling is tried at most once a minute, by `cc-rotate-ctl settle-login` started in the background by a status line tick, by the app on its own thread, or by `cc-rotate-ctl status`; it needs `claude` to run and the network. After 10 minutes an `error` event, `doctor` and the app say so. (Asking the user is no way out: `/status` and `claude auth status` show the identity a swap never updates, F14.)
   A login in the profile that is not known to be the active account's (a `/login` of an account outside the pool, or one left unidentified) is never stored as the active account's by a swap.
   A fresh login of the active account is written into the profile only if that account is still the active one once a stopped swap is settled; then it ends a `/login` of an account outside the pool, and Claude Code's renewals of it are stored again.
   The write-back also re-reads the credentials' change marker before storing, so a login read before a swap's write is never stored under the account the swap made active.
5. Under the locks, read the profile's credentials (`.credentials.json`, or the Keychain item on macOS, section 18) and save its `claudeAiOauth` into the outgoing account's row (`source = swap_out`).
   If that block's refresh token is blank (F8), mark the outgoing account `needs_login` instead.
6. Decrypt the target's `claudeAiOauth`, write it into `.credentials.json` with every other key preserved, using write-to-temp then rename.
7. In one transaction, set outgoing to `parked` (or `needs_login`) and target to `active`, and log `swap` with the triggering sample's windows, the window that triggered it, and the reason the target was picked (section 7.3).
8. Release the profile locks in reverse order, then the swap lock.

Mid-turn behavior: at 98% the active turn keeps running, and its next request goes out on the target account (F1).
A turn that already hit the wall before the swap stopped, and continues once the `StopFailure` hook wakes the session (section 21).

Why this closes the race: any refresh either finishes before step 4, so step 5 captures the rotated token, or starts after step 8, re-reads the file under the lock (F4), and refreshes the target account.
No order leaves a retired refresh token in the store.

## 7. Scheduler

### 7.1 Windows and eligibility

Each window in a sample is classified by its name:

| Name | Kind | Applies to |
|---|---|---|
| `five_hour` | 5-hour | all models |
| `seven_day` | weekly | all models |
| `seven_day_<family>`, `five_hour_<family>` (`opus`, `sonnet`, `haiku`, `fable`) | weekly or 5-hour | that model family |
| any other `seven_day_*` | weekly | all models |
| anything else | other | all models |

An all-models window always applies.
A model-scoped window applies when the rotation profile's most recent `model.id` (recorded on every tick) contains its family, and also when no model is known yet.
Unknown names count as all-models limits, so a new limit system blocks too early rather than too late.
5-hour windows use `swap_threshold_5h`, weekly windows (all-models or scoped) use `swap_threshold_7d` (or the account's `weekly_cap`, when lower, section 7.4), and other windows the lower of the two settings.

An account's usage (`Store::current_usage`) is made from its readings, since each session repeats the numbers of its own last response until its next one (F24): with several sessions the latest reading is often an older one.
- **Windows:** those of its latest sample, plus any window a reading in the 10 minutes before it, and not before the latest reading of the account itself (below), has with a reset still ahead (a session idle since before a window reset shows none of the window that started since; open sessions repeat their numbers at least every 30 s).
  A window none of those has is no longer reported and does not count.
- **Usage of each:** the highest reading of it (the same name, reset times within a minute) since the latest reading of the account itself that has it, that one included, in the order readings were recorded, since usage within a window only grows.
  A reading of the account itself (a usage check, section 20, or another profile's `/usage`, section 9.1; it has no session and does not come from the rotation profile) settles what came before it, which also clears a high reading that was another account's (section 8).
  Such a reading is always recorded, even when it repeats the latest one; other readings that repeat the account's latest within a minute are not.
  So a reading of another account that got recorded (section 8) stays a window's usage until the next reading of the account itself, and so does a genuine drop within a window that keeps its reset time; the account in use gets one only when a threshold swap confirms first or another profile signed in to it reads `/usage`.

A window's effective usage is its percentage, or 0 once its `resets_at` is in the past.
An account is eligible when its state is `parked` and no applicable window is at or above its threshold.
An account with no samples has no windows and is eligible.

Whether an account has a weekly limit (on all models) is detected from its recorded windows, unless `weekly_limit` overrides it:

- **Has one:** a `seven_day` (all-models weekly) window was recorded within the retention period.
- **None:** at least two distinct 5-hour windows (reset times more than an hour apart) were recorded with a reset in the last 8 days, and never a weekly one.
  A real request on a capped account reports the weekly window next to the 5-hour one, so this avoids treating a status line that ran before the first request, or an idle account after its weekly reset, as unlimited.
- **Not known yet:** otherwise.

### 7.2 Ranking and switching back

Ranking, best first:

1. With `prefer_no_weekly_limit` on: accounts without a weekly limit (tier 0).
2. Accounts whose weekly budget would otherwise reset unused (section 7.4), the soonest weekly reset first (tier 1).
3. With `prefer_no_weekly_limit` on: accounts whose weekly limit is not known yet (tier 2), then accounts with one (tier 3); with it off, every other account is tier 2.
   Not known yet sits between the two because such an account may well be unlimited, but should not push out an account known to be.
4. Within a tier (`place`): the active account, then accounts whose all-models 5-hour window is running (its `resets_at` is in the future, or it has usage and no `resets_at`) at least 10 points below its threshold (`RUNNING_MARGIN`), the soonest reset first (no `resets_at` last), then accounts with no running window by `position`, the user's order, then running windows closer to their threshold than that, the most room first.
   With `strict_order` on, `position` alone.
5. The most room: the smallest `threshold - usage` over applicable windows, largest first (the 5-hour threshold for an account without readings), then `label`.

```
tier(a)  = prefer_no_weekly_limit and weekly(a) == none ? 0
         : expiring(a) ? 1
         : prefer_no_weekly_limit ? {unknown: 2, has: 3}[weekly(a)]
         : 2
rank(a)  = tier(a) == 1 ? (1, weekly_reset(a))
         : strict_order ? (tier(a), position(a))
         : (tier(a), 0)
place(a) = strict_order or a is active ? (0, 0)
         : running(a) and five_hour_room(a) >= 10 ? (1, five_hour_reset(a) or infinity)
         : running(a) ? (3, 0)
         : (2, position(a))
margin(a) = every applicable window <= threshold - 5
pick     = min over eligible a != active of (rank(a), place(a), -room(a), label(a))
switch_back_target =
    if not prefer_no_weekly_limit or weekly(active) == none: none
    else if active has a blocking window: none (trigger 1 handles it)
    else min over eligible a with weekly(a) == none and margin(a)
         of (rank(a), place(a), -room(a), label(a))
```

Accounts without a weekly limit always come first, whatever their plan, even when that leaves another account's weekly budget to reset unused: their capacity comes back every 5 hours, while weekly budget spent now is missing later in the week.
An account whose weekly budget would otherwise reset unused (`expiring`, section 7.4) comes next, ahead of every other account, the soonest reset first.

Within a tier, the active account is kept until a limit, and the next pick is the running 5-hour window that resets soonest.
A 5-hour window starts with an account's first request (floored to a 10-minute mark) and resets 5 hours later, and what is left in it is lost then; an account without a running window loses nothing by waiting.
So taking running windows first, the soonest reset first, spends the capacity that expires soonest, which is earliest-deadline-first scheduling.
Simulated in minute steps over 28 days of bursty use (10 random seeds), the order of picks changed the total use served by less than 0.2 points, while keeping the active account and taking running windows first saved about 30% of the swaps.
A swap costs the next request its prompt cache, and every swap is a chance for a session to see a stale reading, so fewer swaps is the gain.
Picking by the user's order alone is `strict_order`.
The windows close to a threshold come last because each would only last minutes, a swap for a few points.

An account can be picked on a reading that is out of date, for example when an agent used it up in its own profile since.
The status line then reports it at its limit on the first request after the swap.
When every reading of the active account since it became active has a window that applies at or above its threshold, the account arrived over its limit, and the threshold trigger skips `swap_cooldown_s` (the 30 s spacing of requests still applies).
This cannot ping-pong: the account it leaves was itself over a threshold, or ranked below it.
Readings that belong to an earlier account are not recorded (section 8, step 2), and a reading that shares a reset time with another account's latest reading does not count as proof either.
Leaving out a genuine reading here only means the cooldown applies as usual.
The swap event records `arrived_over_limit`.

Otherwise the active account is kept until a limit.
The one exception is the switch back: while an account that may have a weekly limit is in use, a tick requests a swap to `switch_back_target`, an account without one, once the threshold-trigger throttling allows it (no request in the last 30 s, `swap_cooldown_s` since the last swap).
So weekly budget is only spent while no account without a weekly limit can be used (with `SWITCH_BACK_MARGIN` to spare), and an account in use for its expiring budget, or picked by hand, gives way too.
It is logged as a swap with reason `preferred_available`.
There is no other switch back: not up the user's order (also with `strict_order`), not to an expiring budget whose week resets sooner, not to balance usage or to reach an earlier 5-hour reset.
The 5-point margin keeps the target from being left again moments later.
Together with the cooldown this rules out ping-pong between thresholds: the target has no weekly limit, so no switch back leaves it, and an account left at a threshold stays above it until its window resets.
A `StopFailure` swap is the exception: the account it leaves may show room it does not have (a limit the status line does not report, or a stop reading that never came), and switching back to it would stop the next turn again, every cooldown.
So the swap records, at its commit, when it left the account (`left_at_stop:<id>` in `meta`); a reading of the account taken while the swap ran is older, so it is not news.
When the account's last reading from before then had no window at its threshold, its room is not trusted (`swap::stop_hold_until`, `Candidate::stop_hold_until`) for `LEFT_AT_STOP_HOLD_MS` (5 hours, by when every 5-hour window has reset), or until a later reading says something different of the windows both report (usage within a point and reset times within a minute count as the same, since the status line and `/usage` round them differently, and an idle session repeats old numbers), or is taken after a window of the reading the account was left on reset.
Whether that reading had a window at its threshold is judged for the model of the session that sent it.
Meanwhile `switch_back_target` skips it, picks take it after every other eligible account, the ranking says why, and a switch-back request it holds up is skipped with that reason.
When that reading did show the limit, there is no hold: the threshold keeps the account out until its window resets, and it is switched back to as soon as it has.
The active account's start is recorded on every swap and adopted login (`active_since`).

Parked accounts have no live samples, which is fine: their last sample plus `resets_at` gives an exact lower bound, and the store never needs to poll Anthropic.
Usage reported by the legacy profiles (section 9) feeds the same numbers, so an account busy in another profile is not chosen blindly.

### 7.3 Explaining picks

The snapshot lists every account in pick order with a short reason ("no weekly limit, in use"; "no weekly limit, 5-hour window already running, resets in 1h 20m"; "no weekly limit, 2nd in your order"; "5-hour limit at 99%, resets in 2h 10m"; "paused"), and the next pick with its reason.
`cc-rotate-ctl next [--explain]` prints them, the dashboard shows "Next: <label> - <reason>", and swap events record the target's reason (`pick`) and, for a switch back, that the target has no weekly limit while the outgoing account has or may have one (`why`).

### 7.4 Weekly budget that would reset unused

What an account with a weekly limit has not used at its weekly reset is lost, and it can only be used as fast as its 5-hour windows let it, while the user works.
So an account moves ahead (`budget::expiring`) once its budget would not fit in the time left otherwise, and not before: until then it stays in reserve for when every other account is at a limit.
`use_expiring_weekly` (on by default) turns this on, and an account's `use_expiring` (on by default; `cc-rotate-ctl use-before-reset`, the account page) leaves that account out: it is never moved ahead, and its hours do not count against the others', since its budget is not planned to be spent early.

Per account with a weekly limit on all models, not left out, parked or active and not on hold, whose weekly window has not reset:

- `left = max(0, weekly threshold - weekly usage)`, the weekly threshold being `min(swap_threshold_7d, weekly_cap)`; below 5 points it is not worth a swap.
- `per_hour = weekly_per_5h * min(five_per_hour, swap_threshold_5h / 5)`: weekly points an hour of use spends, at the account's pace and never faster than its 5-hour window lets through.
- `hours = left / per_hour`.

The accounts are taken in the order their weekly windows reset, since one account is in use at a time and an earlier reset must be met first.
For each, `needed` is the sum of `hours` of it and every account resetting before it, and `available` the working hours expected from when it can be used (now, or when the other window blocking it resets) to its weekly reset.
An account blocked until its weekly reset cannot spend anything and does not count.
It moves ahead when `needed / available >= 0.75`.
An account that moved ahead in this weekly window (`budget_promoted:<id>` in `meta`, holding that weekly reset, written by the swap that took it for its budget, or by a status line tick that finds the account in use expiring) stays ahead while the share is at least 0.3, so that its own spending, which lowers the share, does not make it leave and come back.
An account in use only because the seats were at a limit is held to 0.75 like any other, so its own spending does not keep it ahead and its budget stays in reserve.
So an account that has moved ahead is used whenever it is below its limits and no account without a weekly limit can be used: a 5-hour limit sends the pool to the next account as usual, and the account is picked again at a later swap once its 5-hour window resets.

Three rates come from the last 28 days of readings, each mixed with a cautious guess that the readings outweigh as they accumulate.
Readings come in whole or half points and repeat between changes, so the rates are measured over stretches from one change of the 5-hour window to the next (at most 30 minutes, with readings at most 20 minutes apart, in the same windows, reset times within a minute counting as the same).
Learning reads weeks of readings, so it runs off the status line: before a swap, in the app every minute, and in `status` and `next`, each relearning when the stored rates are 10 minutes old (or from a clock since set back); the status line and the snapshot only read the stored rates.

| Rate | From readings | Guess, and its weight |
|---|---|---|
| `weekly_per_5h`: weekly points per 5-hour point, per account | the growth of the weekly window over the growth of the 5-hour window, over the same stretches | 0.1 (a full 5-hour window is a tenth of the week), worth 50 five-hour points |
| `five_per_hour`: 5-hour points per hour of use, per account | 5-hour growth over the length of the stretches | 10, worth 2 hours |
| activity: the chance of working in each hour of the week | in how many of the weeks seen any account's 5-hour window grew in that hour (at most 1) | 10/24 (10 hours a day), worth 1 week |

The guesses err early: a cheaper window and a slower pace mean more hours needed.
The ranking reason says "weekly budget expires in 1d 4h with 45% left".

`weekly_cap` (per account, `cc-rotate-ctl weekly-cap`, the account page) lowers that account's weekly thresholds below `swap_threshold_7d`, so rotation stops using it there and leaves the rest of its week to the user; budgets, and the dashboard's weekly budget left, are counted up to it.
It changes weekly windows only, not the stricter threshold of windows of an unknown kind.

### 7.5 How long the pool lasts

While an account is in use, the snapshot carries a forecast (`forecast::forecast`) of when, at the current pace, every account would be at a limit, and when the first one frees up after that.

- The pace is the last hour of readings of every account, each 5-hour point divided by that account's usual pace (`five_per_hour`, section 7.4): usual hours of use per hour, 1 being the usual pace.
  Measured across accounts, it carries over a swap, and plans of different sizes count alike.
  Only rises above the highest reading of each 5-hour window count (that reading known from up to 6 hours back), since an idle session keeps repeating its old values.
  The time runs from when work is taken to have started, the typical gap between rises before the first rise of the hour, to now: open idle sessions and background checks do not stretch it, and the pace fades once nothing is used. A single rise shows no pace.
  There is no forecast while the use started less than 15 minutes ago, shows nothing, or the pool is already out (the dashboard says so with its own banner).
- The pool is played forward in 5-minute steps for up to 24 hours with the real pick order (`scheduler::pick`, expiring budgets included): the account in use spends `pace * five_per_hour` 5-hour points an hour and `weekly_per_5h` weekly points for each, a limit hands over to the next pick, an account that may have a weekly limit gives way to one without as soon as one is ready (`scheduler::switch_back_target`, without the cooldown), a 5-hour window starts with its first use and resets 5 hours later, a weekly one resets a week after its reset.
- The first step with no account left is `runs_out_at`; the earliest reset of a usable account after it is `free_again_at`.
- Play goes on past that point, the way sessions stopped at a limit pick up again (section 21): steps with no account left use nothing, and the first account to free up takes over.
- Every stretch an account is in use is a `Turn` in `plan`, oldest first: the account, from and to (epoch seconds), `at_limit` (it ended at a limit, rather than giving way to an account without a weekly limit or being cut off by the horizon), and `rests_until`, when it is usable again after a limit whose reading says when it resets.
  The first turn starts now; gaps between turns are times with no account left.
  An account in use that hands over at once (already past a threshold, as during a swap's cooldown, or giving way to an account without a weekly limit) has no turn: the plan starts with the account that takes over, and the dashboard shows the wait from the account's own `available_at`.

The dashboard draws the plan (section 11) under a headline ("Covered for the next 24 hours", or "Runs out around 3:10 PM" with when the first account frees up), `cc-rotate-ctl status` a line to the same effect, and the app notifies once when the pool would run out within the hour, again only after a forecast has shown room for at least two hours since, or a break from work left no forecast while the pool was not out.

### 7.6 Usage history

`cc-rotate-ctl report [--weeks N] [--json]` (N from 1 to 52, default 4) and the account page (section 11) show how much use each account got, from the recorded samples only (`history` in ccr-core).
Samples older than `sample_retention_days` do not count, even before the next prune removes them.

- **Weekly windows:** for every all-models weekly window (`seven_day`) that reset in the last N weeks, the highest percentage over its samples, how many samples reported it, and when it reset.
  Reset times within an hour of each other are one window, as in section 7.1.
  A window that has not reset yet is still open and is left out.
  Usage within a window only grows, so the highest reading is the last one, and a lower bound when readings stop before the reset.
- **5-hour windows per calendar week:** for the current calendar week and the N - 1 before it (Monday 00:00 to Monday 00:00, local time), how many distinct all-models 5-hour windows were first seen in the week, and how many of them reached `swap_threshold_5h`.
- **Thin data:** a weekly window is thin with fewer than 3 samples, or when its last sample came more than 2 days before its reset; a calendar week is thin with fewer than 3 samples of the account, or when it starts before the retention period.
  A thin entry keeps its recorded numbers and is marked, since the real ones may be higher.
- **No data:** a calendar week without a single sample of the account has no counts at all, never zeros; a weekly window with no sample does not appear.
- Which history describes an account follows its weekly limit as the scheduler sees it (section 7.1): weekly windows for an account that has one, or whose limit is not known yet but has closed weekly windows; 5-hour windows otherwise.

The report prints a table per account, then one summary line per account ("main: used 12% of its weekly limit on average over the last 4 weeks.", "account3: 9 of its 5-hour windows reached the limit in the last 4 weeks (31 used).").
`--json` prints the same data with each account's summary.

## 8. Write-back and the statusline

The profile's `statusLine.command` is `cc-rotate-ctl statusline`, with `refreshInterval` 30 (seconds); it also runs after every assistant message.
The desktop app runs the write-back step (step 3) and triggers 3 and 5 every 5 s as well, so the store stays current and switching back happens when only non-interactive sessions run.
Each tick:

1. Parse stdin JSON.
2. Record `model.id`, if present, as the profile's most recent model.
   If `rate_limits` has any window with a `used_percentage`, insert a sample for the active account with every such window.
   First, per session and Claude Code process (`session_readings`), note since when it has reported these numbers: a reading whose every window is exactly one of the last reading's (a window drops out once its reset passes) is unchanged, anything else starts now.
   A reading unchanged since before the active account became active (`active_since`) is the account the session used before, since it has had no response since (F24), and is discarded, its cost counting for the account it shows.
   That settles every session that reported before the swap, whatever the accounts' reset times; the rules below cover the others (a session that reported first after the swap, and a request started before the swap that finished after it).
   Discard it if any window's `resets_at` equals one of the outgoing account's recorded reset times within 120 s of a swap, as a guard on F5.
   Swaps within 120 s of each other add the outgoing account's reset times to the ones already recorded, so a session idle since two swaps ago is recognized too.
   Beyond those 120 s: a session only notices a new login when it next starts a request (F1), so it keeps reporting the account it used before while it idles, and when a request it started before the swap finishes afterwards (bringing that account's latest usage).
   Such a reading carries the earlier account's reset times. cc-rotate keeps, per account, the reset times known to be its own (`own_resets:<id>` in `meta`, only those still ahead counting): from readings clearly its own, from other profiles signed in to it (section 9.1) and observe mode, and from usage checks (section 20), including the one a swap usually just made of its target.
   Reset times within a minute of each other count as the same, since the status line and `/usage` may round differently.
   A reading is the active account's own when it shares no reset time with another account's latest reading, or has one of the known ones; it belongs elsewhere, and is discarded, when it shares another account's reset time and the known ones differ; otherwise it is ambiguous.
   When its reset time is both another account's and a known one (aligned reset times), the values decide: a reading that repeats another account's latest reading exactly (windows, reset times, percentages within half a point), and is not the active account's latest, belongs elsewhere, since that is what a session still showing that account reports.
   Reset times are aligned to round times, so two accounts' windows can reset at the same moment and status line data alone cannot always tell them apart.
   An ambiguous reading is recorded, since hiding a genuine reading of a used-up account would leave its sessions waiting at the limit, but it does not add to the known reset times, so a stale reading that got through never vouches for the next one; and a threshold swap first confirms the active account's usage with a usage check (section 20) when a window over its threshold got there only by readings of the rotation profile's status line and has a reset time not known to be the account's, or another account's too.
3. If the profile's credentials changed since the last sync (a fingerprint of `.credentials.json`, or of the Keychain item on macOS; not the file's modification time, which Windows stamps from a clock that advances only every 15.6 ms or so, so a renewal right after a swap's write could keep its time), read them.
   A refresh token fingerprint other than the active row's is a login cc-rotate did not write: Claude Code's renewal of the active account's login, or a `/login` in the profile.
   When `.claude.json` names a different account than it did when last read, that is a `/login`, acted on at once: a pool account becomes active with that login (an `adopted_login` event), and an account outside the pool marks the profile foreign (a `foreign_login` event), after which nothing is stored from the profile until a swap or a re-login writes a pool account's login into it.
   Otherwise the profile alone cannot tell a `/login` from a renewal, since `.claude.json` keeps naming the account it named before the swaps since (F14): the login is stored only once Claude Code says whose it is (section 20.5), which the tick starts in the background.
   With usage checks off or stopped, it is stored as the active account's at once (`source = sync`), and a `/login` of the account `.claude.json` already names goes unnoticed.
   This keeps the store a few seconds behind Claude Code's own refreshes.
4. Evaluate triggers 1, 3 and 5 and spawn a detached swap if needed.
5. Forward the original stdin to the `statusline_downstream` command (if set) and print its output, prefixed with the active account label.

Budget: one `cc-rotate-ctl statusline` run without a downstream command (process start plus steps 1 to 4) completes in under 30 ms at the 95th percentile; the downstream command's own run time is added on top and is outside cc-rotate's control.

## 9. Usage reporting from the legacy profiles

The legacy profiles can run `cc-rotate-ctl statusline --observe` in front of their existing statusline.
Observe mode only records samples, attributed by `oauthAccount.accountUuid` from that profile's `.claude.json`, and tags them with the profile name.
It never touches credentials or triggers swaps.
This lets the dashboard show every account during a migration, and lets the scheduler avoid accounts the legacy profiles are draining.

### 9.1 Readings the other profiles already hold

Without any opt-in, cc-rotate reads the usage reading Claude Code cached in each of the user's other profiles (F16): every `.claude*` directory in the home directory except the rotation profile, with `~/.claude.json` for the default profile.

- A reading counts for a pool account when the profile's `oauthAccount.accountUuid` names it, the cache is stamped with the same id, and the profile's `oauthAccount.organizationUuid` is the account's organization; anything else is ignored.
  One person can belong to several organizations with one account id (a personal plan and a Team seat), and limits are per organization.
  A reading taken before a `/login` to another organization of the same person still carries the same stamp, so the organization is checked as the profile names it now; a profile switched between organizations can misattribute its last reading until it reads usage again.
- A profile whose status line is `cc-rotate-ctl statusline` without `--observe` is a rotation profile or a copy of one, whose login changes account (F14), and is skipped.
- It becomes a sample with the cache's `fetchedAtMs` as its time (at most now), tagged with the profile's folder name like observe mode, and only when it is newer than the account's latest sample.
- The account's windows that a report cannot express (any name other than `five_hour`, `seven_day` and their model-family forms) are carried into the new sample at its usage (section 7) while their reset has not passed, so a limit only the status line reports does not stop counting.
- Windows come from `limits[]` (older bodies: the `five_hour`, `seven_day`, `seven_day_opus` and `seven_day_sonnet` fields) and are named as the status line names them: `session` is `five_hour`, `weekly_all` is `seven_day`, and a row scoped to a model family is `five_hour_<family>` or `seven_day_<family>`.
  Rows of another kind, rows scoped to another product (`scope.surface` other than Claude Code) and rows scoped to a model family cc-rotate does not know are left out: the report covers the whole plan, unlike the status line, so a guess could park an account for days over a limit that does not apply, while a limit that does apply and was missed shows up in the status line on the first request (section 7.2).
- A config file is parsed again only after its modification time changed (`profile_usage_seen:<path>` in `meta`), and only its `oauthAccount` and `cachedUsageUtilization` are deserialized, so this stays cheap even though `.claude.json` files can be large.
  A profile signed in to an account outside the pool is not marked as read, so its reading is picked up once that account is added.
- It runs before a swap picks its target (section 6), in the background sync (the app every 5 s, and `cc-rotate-ctl status`), and in `cc-rotate-ctl next`, but not in the status line tick, whose time budget it does not fit.
- It only reads those files; it never reads their credentials.

## 10. Login flow

Used both for adding an account and for re-logging an account in `needs_login`.

1. Create `<data dir>/staging/login-<uuid>/`, mode 0700 on Unix, and record in its `claude.pid` the process making the login (the app or `cc-rotate-ctl login`) with its start time.
2. Spawn `claude auth login --claudeai --email <email>` with `CLAUDE_CONFIG_DIR` set to the staging directory, piping stdin, stdout and stderr.
   `--email` is omitted when adding a new account with no known email.
3. Parse the sign-in URL from stdout and show it, plus a paste-code field that writes to the child's stdin (F9).
   Claude Code opens the browser itself.
4. On exit code 0, read the staging credentials' `claudeAiOauth` (the file, or on macOS the staging directory's Keychain item) and the staging `.claude.json` `oauthAccount`.
5. For a re-login, refuse the import if `accountUuid` differs from the target account, and tell the user which email actually signed in.
6. Upsert the account and its credentials (`source = login`).
   A re-logged account goes to `parked`, or to `active` if the pool had no active account.
7. Delete the staging directory, including on failure, cancel, and the 10-minute timeout.
   `cc-rotate-ctl login` keeps running through Ctrl+C until Claude Code, which gets it too, has exited, so it still deletes it.
   The app runs the sign-in as a process tree (a job object on Windows, which also ends it if the app dies; a process group on Unix), and stops every sign-in still running when it quits.
   A staging directory whose recorded process is gone, or without a record and older than the timeout (as older versions named them, a bare `<uuid>`), is deleted with its Keychain item by `usage_check::sweep_logins`: when a sign-in starts and when the app starts.

`claude auth login` and `claude auth status` run without the `ANTHROPIC_*` and `CLAUDE_CODE_*` variables usage checks drop (section 20.1), so an inherited token can't stand in for the login being made.
An import that would replace an account's login with one for another organization of the same Claude account (one person can belong to several under one account id) is refused: cc-rotate keeps one login per account.

Rules:

- Every account in the pool gets its own fresh login.
  Tokens are never copied from the legacy profiles, because a shared refresh token would break whichever holder refreshes second.
- The browser signs in as whatever claude.ai account it is currently logged into.
  The UI states the expected email before opening and suggests a separate browser profile per account when the wrong one keeps signing in.
- `cc-rotate-ctl profiles` lists the user's other `.claude*` profiles in the home directory and the account each belongs to, read from its `.claude.json`.
  `cc-rotate-ctl login --from-profile <name>` starts a fresh login for that account with its email and label pre-filled, and refuses the import if a different account signs in.
  Discovery is read-only: it reads a profile's `.credentials.json` only to tell whether it is signed in, and never imports or writes it.

## 11. Dashboard app

`cc-rotate-app` is a Tauri 2 window plus a tray icon; closing the window hides it to the tray, and `cc-rotate-ctl dashboard` launches or focuses it.
It is single-instance, starts at login (toggle in the app), and exposes no network port: the UI talks to the Rust side only through Tauri commands and events.
The first launch of an installed copy turns starting at login on; while it is on, every launch points it at the copy running, so it follows the copy an install puts in place.
A copy run from a Cargo build folder (`target/<profile>/`, marked by Cargo's `CACHEDIR.TAG`) leaves it alone, since login would start a build the next one replaces, and an install could not update it.
On Windows, `install.ps1` closes an app started from the build folder before building, since it holds its executable open, and starts the installed copy in its place.
The window's capability grants only listening for the app's events, beyond its own commands, and the CSP allows nothing but the app's own files and its IPC.
`set_setting` takes only the settings the Settings page shows; the ones that name a program to run or where the login is written (`claude_path`, `statusline_downstream`, `profile_dir`) are `cc-rotate-ctl config` only.
`open_login_page` reopens the sign-in page Claude Code announced for a running sign-in, and opens nothing else.
The tray tooltip shows the active account, its 5-hour and weekly percentages (or that it has no weekly limit) and the next pick, refreshed on every store change and every 30 s; the tray menu offers Open, Swap now, and Quit.
Native notifications fire for `pool_exhausted`, `dead_login`, any account entering `needs_login`, and "<label> is ready again" when the pool stops being exhausted.
The watcher also starts the background usage checks (section 20.2).
The UI is TypeScript built with Vite; its charts are SVG it draws itself, with no chart library.
Light and dark themes follow the system.
UI copy uses no em dashes.

The window has a sidebar and a page.
The sidebar lists the pages (Overview, Activity with the swaps of the last 24 hours, API cost, Settings), then every account in the user's order: its color, label, state ("In use", "Ready", "Next", the time it is back from a limit, "Paused", "Sign in"), and a thin bar of its 5-hour window left; a + adds an account.
Each page has a header with its title and actions, and a banner under it for a swap left unsettled, any `needs_login`, sessions waiting at a limit, `pool_exhausted` (on pages other than the overview, whose headline says it), or sign-ins ending soon.

Order: dragging an account by its handle, in the sidebar or the plan, reorders the accounts; a focused handle moves with the arrow keys (Home and End for first and last), and the account page has Move up and Move down.
The drag uses pointer events rather than HTML drag and drop, which the platform webviews handle inconsistently.
The new order shows at once and is saved in the background, one save after another.

Views:

  Then the **plan**: 12 hours from the start of the hour at least half an hour ago (so now is never at its edge), one row per account in the user's order.
  A row has a drag handle, the account's color, label and plan ("Max 5x", "Max 20x", "Team", "Team 5x", "Pro", else the raw subscription type), a state line ("In use, 8% of 5 hours used", "Back 1:35 AM", "Ready, 9% of its week used", "Next", "Paused", "Signed out"), and its lane.
  The lane draws the forecast's turns: the active account's as a solid bar from when it was swapped in, later ones as tinted bars with their times ("1:06 AM to 3:46 AM"), and each wait for a limit to reset as a hatched bar ("back at 3:25 AM"); an account at a limit now is hatched until it is usable again.
  Each bar shows the longest label that fits it, measured after layout and again when the window is resized.
  A line marks now, hour lines run behind the lanes, and a band across every lane marks a stretch with no account left.
  A lane with nothing in it says why: not needed before the end of the plan, paused, signed out, or the reason it is not available.
  Without a forecast, the active account's bar runs from when it was swapped in to now, and accounts at a limit are hatched until they are back.
  Rows offer Use now (on hover), Resume, or Sign in; clicking an account opens its page.
  Under the plan: a key to the bars, how cc-rotate uses the order as the settings make it, and the weekly budget left (summed weekly percentage remaining over usable accounts with a weekly limit, in accounts).
  Then the charts, and the latest activity with a link to the Activity page.
- **Account page:** the label, plan, state and email in the header, with Use now, Pause or Resume, Check usage, and Sign in again.
  The 5-hour and weekly meters, each with the swap threshold marked and when it resets ("No weekly limit" when it has none), and model-scoped windows.
  Details: where its latest reading came from ("updated 5m ago", "updated 5m ago from work", "checked 5m ago"), organization, **Recent weeks**, **API value**, extra usage, its place in the user's order with Move up and Move down, its place in the pick order with the reason, when its login was updated and its sign-in ends, its usage checks, and its warm-ups (section 23).

  Its settings: label, the weekly limit override (detect, has one, none; saved when picked), the weekly cap, use before reset, keep the 5-hour window running, and Remove account (asked twice, and not for the active account).
  The settings are built when the page opens, so a refresh never undoes what is being typed.
- **Charts:** a panel with two tabs, **Usage limits** and **API cost**, each over the last 24 hours or 7 days.
  Each says in a line what it shows, has a legend naming every account by its color, and shows the values under the pointer in a tooltip.

    The read-only `costs` command returns the hourly buckets (`account_costs`) from the hour holding a given time on; an hour's cost goes to the day its hour starts in.
- **API cost page:** the API cost chart alone, and a table of each account's API value over the last 24 hours, 7 days and 30 days, with the totals.
- **Activity:** the log of swaps, logins, problems and setting changes by day; renewals, skipped swaps, version notes, warm-ups and reorders show when asked for.
- **Login:** the section 10 flow in a dialog with live status (waiting for browser, received, imported, failed).
- **Settings:** the settings in groups (when to swap, which account comes next, usage checks and sign-ins, start at sign-in), `doctor` results (section 12), the app and Claude Code versions, and the profile and data folders.

### 11.1 In the terminal

`cc-rotate-ctl watch [--interval S]` (S from 1 to 3600, default 2) is the dashboard for SSH sessions and terminal panes, where there is no app or tray: a header line with the time of the last refresh, the `status` output (which includes the next pick), and as many of the latest events as fit, redrawn every S seconds.

- It is read-only: each frame is a snapshot (`snapshot::snapshot` and the events table, which only read the store).
  Unlike `status`, it never syncs the profile's login, swaps, settles a login or starts Claude Code; the status line and the app keep the store current.
- It uses crossterm for raw mode, keys, the terminal size and the alternate screen, which behave the same in Windows Terminal, conhost, macOS Terminal, Linux terminals and over SSH.
- No flicker: each frame moves the cursor home, overwrites the previous one line by line, clears what is left of each line and then everything below the last; it never clears the whole screen.
  Lines are cut to the width in terminal columns (wide characters such as CJK and most emoji take two, and one that would cross the edge is left out) and frames to the height (keeping the newest events), so the screen never wraps or scrolls.
- The cursor is hidden while it runs.
  q, Esc and Ctrl-C quit (raw mode delivers Ctrl-C as a key, on Windows too), and the terminal is restored on every exit, including an error.
  On a panic, a panic hook restores it before the panic message is printed, so the message stays on screen; the guard puts the previous hook back.
  On Unix, SIGTERM, SIGHUP, SIGQUIT and SIGINT (Ctrl-C itself arrives as a key in raw mode, but `kill -INT` does not) only set a flag while it runs (the wait between frames checks it every 100 ms); the terminal is restored, and the process then ends the way the signal would have ended it.
- When stdout or stdin is not a terminal (piped output, `watch < /dev/null`), it prints one frame without the cursor movement and exits.
  Without a terminal on stdin, crossterm would read keys from `/dev/tty`, which it cannot poll on macOS without its `use-dev-tty` feature, so this keeps every platform the same and never hangs.

## 12. Errors, health and version safety

- Every failure path logs an `events` row and leaves `.credentials.json` either untouched or fully written, never partial.
- `cc-rotate-ctl doctor` checks:
  - the Claude Code version against the tested list,
  - that both lock paths resolve as expected,
  - that the profile's `statusLine` and `StopFailure` hook point at cc-rotate, and that the hook is this release's (`asyncRewake`), else run `setup --keep-existing`,
  - that nothing overrides the profile's login (`ANTHROPIC_AUTH_TOKEN` or `CLAUDE_CODE_OAUTH_TOKEN` in the environment or the profile's `env`, or an `apiKeyHelper`; `ANTHROPIC_API_KEY` only warns, since Claude Code asks before using it), and that `CLAUDE_CODE_RETRY_WATCHDOG` is not set (F11),
  - whether herdr is present (`HERDR_ENV` in a pane, or `herdr` found like `claude`, section 4.4) and the `SessionStart` hook is installed, warning only when herdr is present and would resume sessions with plain `claude` (section 19),
  - where Claude Code keeps the profile's login (file or Keychain item), failing if the Windows Credential Manager backend is on (section 18.2) or this session cannot use the macOS Keychain (section 18.1),
  - that no PowerShell profile still defines the old `cc-rotate` function,
  - that exactly one account is active, or that zero are and every account is `needs_login` or `paused`,
  - that `.credentials.json` matches the active account's `account_uuid` by fingerprint,
  - that every stored login decrypts, and where the key file is (warning if other users can read it),
  - whether usage checks are on, and every account whose last check failed, with the reason.
- On an untested Claude Code version, rotation still runs, the dashboard shows a warning, and the next manual verification uses the E2E suite below.
- Back up `.credentials.json` before the first swap of each day to `<data dir>/backups/credentials-<day>.ccr`, sealed as in section 5.1, keeping 7; `cc-rotate-ctl backup <file>` prints one.

## 14. Requirements

1. R1: A swap changes the account used by every running CLI session in the profile on that session's next API request, with no restart.
2. R2: No interleaving of a Claude Code token refresh and a swap leaves any account's stored refresh token retired.
3. R3: A swap writes only `claudeAiOauth`; `mcpOAuth` and every other key in `.credentials.json` parse to the same values before and after.
4. R4: Concurrent triggers from many sessions produce at most one swap per `--from` account.
5. R5: No automatic swap happens within `swap_cooldown_s` of the previous swap, except for `StopFailure`, a dead login, or a threshold on an account that arrived over its limit (section 7.2).
6. R6: When no account is eligible, nothing changes, and the dashboard shows a banner and (while the app runs) a native notification.
7. R7: The store and its backups never hold plaintext tokens on disk; they are sealed with authenticated encryption under a key file only the user can read (section 5.1).
8. R8: cc-rotate makes no network requests to Anthropic; the only requests it causes beyond the user's sessions and sign-ins are the usage checks Claude Code makes (section 20).
9. R9: The statusline path meets the section 8 latency budget.
10. R10: The login flow imports a working login without the user opening a terminal, and rejects a re-login that signed in as a different account.
11. R11: The legacy profiles' credentials are never read for import or written.
12. R12: Every swap, skip, login, sync and error is visible in the dashboard events view within 2 s.
13. R13: An account is never picked while a window that applies to the model in use is at or above its threshold, whatever the window's name.
14. R14: With `prefer_no_weekly_limit` on, no account with a weekly limit is picked while an eligible account without one exists.
15. R15: The only switch back goes from an active account that may have a weekly limit to an eligible account without one, with `SWITCH_BACK_MARGIN` to spare, never within `swap_cooldown_s` of the last swap, never to an account a `StopFailure` swap left at a limit its readings did not show, until a different reading of it or `LEFT_AT_STOP_HOLD_MS`, and never with `prefer_no_weekly_limit` off, whatever `strict_order` says.
16. R16: Usage is attributed only to the account whose login produced it (F5, F14, F16, and the organization check in section 9.1); upgrading the store keeps every sample and the account order.
17. R17: A usage check never runs with a renewable copy of the active account's login, never deletes a login Claude Code may have renewed during it before storing it (including when the check dies or is killed), holds back an account whose login it cannot vouch for until a check settles it, never lets Claude Code run `/usage` as a prompt twice, and no automatic check of an account runs before the usage endpoint's `retry-after` ends.
18. R18: No automatic warm-up runs for an account the user did not opt in (only `cc-rotate-ctl warm-up`, when asked), and none for the account in use; a warm-up holds every guarantee of R17 for both of its runs; and one whose result shows another model, more than one turn or a cost above `WARM_MAX_COST_USD` stops warm-ups until the user turns one on again.

## 15. Testing

Unit tests (`cargo test`): window classification and applicability, the weekly-limit detection table, ranking keys, switch-back hysteresis (a simulated day of ticks with no ping-pong), plan labels, the schema 2 to 3 upgrade, scheduler eligibility, effective-usage reset math, credfile merge preserving unknown keys, store invariants, the encryption round trip with tamper and wrong-account rejection, the key file's creation and permissions, the DPAPI store conversion (against real DPAPI blobs on Windows), lock interop against a real proper-lockfile holder in a child process, the mapping of usage reports to windows (recorded Team and Max bodies), the attribution rules for other profiles' cached readings, the arrived-over-limit exception to the cooldown, the usage history (open windows left out, moved reset times merged, thin and empty weeks, retention, accounts without data) and its summaries, and that a snapshot, the history and a `watch` frame never write to the store.
Integration tests cover a swap that skips an account its own profile used up, and an account found used up after a swap being left on the next reading.

`cargo run -p ccr-core --example replay -- [--store <store.db>] [--days N]` replays recorded use through `scheduler::decide` and `scheduler::pick`, once with `strict_order` and once without, and prints the use served, the swaps by reason, the 5-hour windows started and the 5-hour points left unused in windows that were used.
The demand is the rises of the cc-rotate profile's 5-hour readings in hours of each account's usual pace, spread over the minutes since the reading before (at most 20).
Other profiles' readings are left out, but a rise after the rotation profile returns to an account includes their use in between, and weekly-limit detection is taken at the end of the period, so the numbers compare policies rather than predict the pool.
It copies the store with `VACUUM INTO` from a read-only connection and opens only the copy; the database is never written, though SQLite may create its `-wal` and `-shm` files next to it.
On 23.1 hours of the author's pool (five Team seats and two Max accounts, 27.5 hours of use at the usual pace), both served all of it with 8 swaps (1 switch back, from a Max account to a seat), leaving 25 five-hour points unused in windows that were used.
The real day, under earlier rules that also switched back within a tier, had 22 swaps (11 switch backs, 3 by hand).

End-to-end tests against the real `claude` in a throwaway profile, with two real accounts (the user logs in once per account at the start):

- E1 (R1): start a session, swap A to B, send a prompt; `claude auth status --json` in the profile and the statusline's `resets_at` both reflect B.
- E2 (R2): set A's `expiresAt` in the file to the past so the next request refreshes, then fire a swap while that request is in flight; swap back to A and complete a request successfully.
- E3: park A until its access token expires, swap back, and confirm Claude Code refreshes from the stored refresh token.
- E4 (R4): ten sessions over threshold at once produce exactly one `swap` event.
- E5 (R10): add and re-login an account from the dashboard, including the wrong-account rejection.
- E6 (R11): run `claude auth status` in each legacy profile before and after the suite; results are unchanged.
- E7 (F5 guard): after a swap, no sample is attributed to B with A's `resets_at`.
- E8 (F11): with one account genuinely at its limit and swaps paused, start a turn so it sleeps at the wall, then resume swaps; the turn continues on the target account without user input.
  Record the time from swap to resumed response as the measured recheck latency, and if it exceeds 5 minutes, add a mitigation to this spec before release.
- `StopFailure` is verified with a recorded hook payload, since a real limit cannot be produced on demand, and end to end by `tests/e2e/wait-at-limit.py` (section 21.4).
- E10 (section 20): `cc-rotate-ctl check` reads every account not in use, and the readings match each account's `/usage` (verified 2026-10-24 on Windows with six real accounts, about 2.5 s each).
- E11 (R17): with a parked account's stored access token marked expired, a check makes Claude Code renew the login, the store holds the renewed login afterwards (`source = check`), and a second check works with it (verified 2026-10-24 on Windows).
- E9 (section 9.1): with an account used up in its own profile, `cc-rotate-ctl next --explain` lists it as over its limit with the reset time that profile's `/usage` shows, and the next swap skips it.

## 17. Decisions

1. Both swap thresholds default to 98%.
2. Every account joins the pool through a fresh login made inside cc-rotate (section 10).
   E2E tests E1 to E7 need two logged-in accounts; E8 needs one account genuinely at its limit.
3. There is no reserve concept in v1: every `parked` account is eligible, and `paused` is how a user holds one back.
4. The project is open source under the MIT license; no code or doc may assume a particular user, path, or account count.
5. Windows and Linux are supported; the store's encryption is the same on every platform (section 5.1).
   Platform-specific code (process flags and detaching, the launcher's signal handling, command quoting, the DPAPI conversion) sits behind `cfg(windows)` and `cfg(unix)`.
   CI builds, lints and tests the whole workspace, including the desktop app, on Windows, Linux and macOS.
6. Limits are modelled generically (section 7.1), because cc-rotate is not built for one set of plans.
   Accounts without a weekly limit are used first; the account in use is kept until a limit, then running 5-hour windows go first (the soonest reset first), then the user's order, then the most room; the only switch back is from an account with a weekly limit to one without, as soon as one is usable (section 7.2).
   A switch back also overrides an account picked by hand; pausing is how a user keeps an account out.
7. Whether an account has a weekly limit is detected from its usage, with a per-account override, never assumed from its plan: some Team seats report no weekly limit although plans normally have one.

## 18. Credential storage per platform

Claude Code 2.1.310 picks its credential storage per platform build, and cc-rotate mirrors it in `credstore`:

| Platform | Where Claude Code keeps the credentials document |
|---|---|
| Windows | `<CLAUDE_CONFIG_DIR>/.credentials.json`, unless the Credential Manager backend is on (below) |
| Linux | `<CLAUDE_CONFIG_DIR>/.credentials.json` only |
| macOS | A login Keychain item, with `.credentials.json` as the fallback |

### 18.1 macOS Keychain

- The item is a generic password with service `Claude Code-credentials-<h>`, where `<h>` is the first 8 hex digits of SHA-256 over the NFC-normalized `CLAUDE_CONFIG_DIR` string exactly as given (no suffix when the variable is unset), and account `$USER` (else the OS user name; `claude-code-user` when it has characters outside `[A-Za-z0-9._-]`).
  The `cc-rotate` launcher sets the variable to the recorded profile path, so cc-rotate and Claude Code compute the same name.
- The item holds the same JSON document as the file.
  Claude Code reads it with `security find-generic-password -a <user> -w -s <service>` and writes it with `security -i`, feeding `add-generic-password -U -a "<user>" -s "<service>" -X "<hex of JSON>"` on stdin (on the command line instead when that line is over 4032 bytes).
  cc-rotate runs the same commands through `/usr/bin/security`, so items Claude Code created never prompt, and confirms each write by reading the item back.
- Reads take the Keychain item when there is one, else the file; exit code 44 (no item) and 36 (Keychain locked or no GUI session, for example over SSH) fall back to the file, as in Claude Code.
- Writes go where the document is now. A profile with no credentials anywhere gets the file, which Claude Code reads as its fallback and moves into the Keychain on its own next write.
- macOS gives the login Keychain only to programs started from the desktop session, so in a session started over SSH, or by a program that was (a herdr or tmux server started from an SSH connection), `security` answers 36: to reading an item's password, and to `show-keychain-info`, which cc-rotate asks since it answers so whether or not the profile's item exists (a missing item reads as 44 either way).
  Claude Code 2.1.310 there finds no login in the Keychain, and does not save one to the file either while the Keychain is locked (`keychain_locked_skip_fallback`): a login it signs in to or renews is lost, with the refresh token it replaced.
  So in such a session (`Credentials::complete` false) the `cc-rotate` launcher refuses to start Claude Code (section 4.4), a swap is skipped (it would write the file, which the desktop session's sessions do not read), and `doctor` fails the login storage check.
- Claude Code caches a Keychain read for 30 s and has no mtime to compare, so a swap reaches running sessions within about 30 s rather than on the next request (R1 is relaxed to that on macOS).
  cc-rotate's statusline detects changes with a fingerprint of the item, as it does for the file.
- The refresh locks are the same directories as on the other platforms.
- A login made in a staging directory lands in that directory's Keychain item; the staging cleanup deletes the item along with the directory, on success, failure, cancel and timeout.
- To verify on a Mac: the `credstore` unit tests (service names against values computed with Claude Code's own expression), then E1 to E7 with the 30 s allowance.

### 18.2 Windows Credential Manager

Claude Code 2.1.310 on Windows also contains a `credential-manager` backend (with the file as fallback).
It is used when `CLAUDE_CODE_FORCE_WINDOWS_CREDMAN=1`, or when the server-side flag `tengu_windows_credman` is cached as on: `cachedGrowthBookFeatures.tengu_windows_credman` in `<CLAUDE_CONFIG_DIR>/.config.json` when that file has content, else in `<CLAUDE_CONFIG_DIR>/.claude.json`.
With it on, swaps written to the file would no longer reach running sessions, so `doctor` fails the "Claude Code login storage" check.

## 19. herdr session resume

[herdr](https://github.com/herdrdev/herdr) is a terminal workspace manager for coding agents.
When its server restarts it restores each pane and, with `resume_agents_on_restore` (on by default), resumes the agent session that ran there.
For Claude Code its built-in command is `claude --resume <id>`, which runs on the default profile, so a cc-rotate session would come back outside the pool.
herdr 0.9.2 and newer let an integration report its own resume command, and a reported command wins over the built-in one on restore.
These behaviors were read from herdr's source at 0.9.4 and confirmed against an isolated herdr instance.

| # | herdr behavior | Why it matters |
|---|---|---|
| H1 | `herdr pane report-agent-session <pane> --source <id> --agent <label> [--seq <n>] -- <argv...>` records a resume command for the pane. `--source` is free-form except for the reserved `herdr:` prefix, and `--seq` orders reports per source: an older one exits 0 but is ignored. | cc-rotate reports under `cc-rotate` with the hook's time in ms as `--seq`, so a late report never replaces a newer session. |
| H2 | The command is rejected (`invalid_resume_argv`) unless the first element is a bare name (`[A-Za-z0-9_.-]`, not starting with `-`), no element has an apostrophe or a control character, and there are at most 64 elements and 8 KiB. | The command is exactly `cc-rotate --resume <session id>`, and a session id that is not a plain token is refused before reporting. |
| H3 | Until herdr has seen a `claude` process in the pane (any descendant of the pane's shell), the report fails with `resume_not_accepted` (CLI exit 1, JSON error on stderr). A rejected report does not consume its `--seq`. | The report is retried every 500 ms for up to 15 s with the same `--seq`; in practice herdr accepts it within about half a second. |
| H4 | On restore, herdr starts the pane's default shell and types the command and Enter, quoting arguments POSIX-style. | `cc-rotate` must be on `PATH`; plain tokens type the same in every shell. |
| H5 | When the `claude` process exits, herdr clears the reported command and its own saved session for the pane. | No `SessionEnd` hook is needed. `release-agent` is never called (it would also fire on `/clear` and race the new report), and neither is `report-agent`, which would take over the pane's status display. |
| H6 | Panes get `HERDR_ENV=1`, `HERDR_PANE_ID`, `HERDR_SOCKET_PATH` and `HERDR_BIN_PATH` (the herdr executable), which hooks inherit. herdr's own Claude Code hook (`herdr-agent-state`, copied into the rotation profile by setup with the rest of the hooks) reports only the session id, under `herdr:claude`. | The hook finds the pane and the right server from the environment, and the two reports do not interfere. |

The flow:

1. `setup` adds a `SessionStart` group with matcher `^(startup|resume|clear|compact|fork)$` running `cc-rotate-ctl hook session-start` with a 10 s timeout (section 4.3).
2. The hook exits at once unless `HERDR_ENV=1` and `HERDR_PANE_ID` are set.
   It skips subagents, which carry a non-empty `agent_id` (`agent_type` alone is also set for a main session started with `claude --agent`), takes `session_id`, and starts `cc-rotate-ctl herdr-report --seq <now ms> -- <pane> <session id>` in the background with the same detaching as the background swap.
   The detached process keeps none of the hook's standard handles, so Claude Code's startup never waits for it.
   The hook prints nothing, since Claude Code adds a `SessionStart` hook's output to the session's context.
3. `herdr-report` runs `$HERDR_BIN_PATH` (else `herdr`, found like `claude`) with `pane report-agent-session <pane> --source cc-rotate --agent claude --seq <n> -- cc-rotate --resume <session id>`, retrying `resume_not_accepted` as in H3.
4. Every failure goes to the log; none reaches Claude Code.

Sessions started before the hook was installed keep herdr's built-in command until they start again in a covered way (a new start, `--resume`, `/clear`, or compaction).
Testing: unit tests cover the hook input, the command against H2, and the settings merge; an integration test drives the hook and the report against a fake `herdr` that refuses twice; the end-to-end check restarts an isolated herdr server and confirms the restored pane runs `cc-rotate --resume <id>`, and that quitting the session clears the report.

## 20. Usage checks

The status line only reads the account in use, and the other profiles' readings (section 9.1) only exist for accounts used there.
A usage check reads an account with Claude Code's own `/usage` (F17).

### 20.1 One check

1. Take the account's lock, `<data dir>/locks/account-<id>.lock` (proper-lockfile semantics like the swap lock), without waiting for an automatic check and up to `lock_timeout_ms` for one the user asked for.
   A swap takes the same lock before it reads the account's stored login to write it into the profile (section 6), and so does a re-login of an existing account (waiting up to `lock_timeout_ms` plus the 60 s a check may run), so no two of them use one login at once.
2. Recover what an earlier check that died left behind (20.3), then re-read the account under the lock: an active account (its status line reads it), an account that needs a login, and a paused one (unless the user asked) are not checked, and neither is an account whose stored login is the one the rotation profile holds (a swap that stopped half way can leave it there): Claude Code renewing it in the check would sign the profile's sessions out.
3. Create a scratch profile `<data dir>/staging/check-<id>-<start ms>-<uuid>/` holding the stored `claudeAiOauth` in `.credentials.json`, and in `start.fp` the fingerprint of that login.
   No identity is given: Claude Code fetches the account's profile itself and stamps the reading with the account the login really belongs to.
   When the account is held back (20.3), the login's `expiresAt` is set to 0, so Claude Code renews it and the check settles whether it still works.
4. Run `claude -p /usage --output-format json --debug-file <scratch>/debug.log` with `CLAUDE_CONFIG_DIR` set to the scratch profile, the scratch profile as the working folder, every `ANTHROPIC_*`, `CLAUDE_CODE_*`, `CLAUDECODE*` and `HERDR_*` variable removed except how Claude Code reaches the network and finds Git Bash (`CLAUDE_CODE_GIT_BASH_PATH`, `CLAUDE_CODE_CERT_STORE`, `CLAUDE_CODE_CLIENT_CERT`, `CLAUDE_CODE_CLIENT_KEY`, `CLAUDE_CODE_CLIENT_KEY_PASSPHRASE`, `CLAUDE_CODE_HTTP_PROXY`, `CLAUDE_CODE_HTTPS_PROXY`), `DISABLE_AUTOUPDATER=1`, and no console window on Windows.
   Its output goes to files in the scratch profile (no pipes a stray process could hold open), its process id to `claude.pid`, and it runs as a process tree (a job object that kills the tree when closed on Windows, which also happens if cc-rotate dies; its own process group on Unix) that is killed as a whole after 60 s (30 s before a swap).
5. Read the scratch profile: its login (the file, or on macOS the scratch profile's Keychain item), its `cachedUsageUtilization`, the result on stdout and the debug log.
   When the login cannot be read, nothing is decided: the scratch profile stays for 20.3, and the account is held back.
6. When the result shows a model turn (`num_turns` above 0, a `total_cost_usd` above 0, or output tokens), Claude Code ran the text as a prompt, a model request on the account's quota: checks stop (`usage_checks_blocked` in `meta`, an `error` event) until the user sets `usage_checks` again. An error result is only a failed check.
7. In one transaction:
   - a login whose refresh token changed is stored (`source = check`, a `sync` event with reason `usage_check`), and a blanked one (F8) marks the account `needs_login` with a `dead_login` event;
   - a reading fetched during this check and stamped with the account's id becomes a sample (`profile = check`), named as in section 9.1, with the account's windows a report cannot express carried over at its usage (section 7), and its reset times become the account's own (section 8);
   - a reading stamped with another account's id means the stored login belongs to that account: the account is marked `needs_login` with an `error` event;
   - the account's check state (`usage_check:<id>` in `meta`: last attempt, last reading, `not_before`, `held_back`, the last failure for people) is updated;
   - when the account's stored login or state changed during the check (a `/login` in the profile adopted it), the check's verdict on the old login (a renewal, a rejection, another account) is dropped; its reading still counts.
8. Only after the transaction commits, delete the scratch profile and its Keychain item.

A 429 (the debug log's `429 remembered ... not asking again for <n>s` from the usage fetch, else 5 minutes) sets `not_before` to when the endpoint will answer again, between 1 minute and 1 hour; any other failure sets it `usage_check_interval_s` ahead.
On Windows, checks do not run while the rotation profile uses the Credential Manager backend (section 18.2), and a check that finds Claude Code switched to it stops checks and holds the account back, since a login it renewed there is invisible to cc-rotate.

### 20.2 When checks run

- Before a swap (section 6, step 3), for a pick whose latest reading is older than `usage_check_max_age_s`, unless the request names its target.
  This keeps a swap from landing on an account that was used up where cc-rotate could not see it, and gives the account's own reset times for section 8.
- In the app, every minute, at most one at a time (`usage_check::next_job`): first a held-back account not tried in the last 5 minutes, then a warm-up that is due (section 23), then the first account in pick order that is parked, has no reading and no check attempt newer than `usage_check_interval_s`, and whose `not_before` has passed (`usage_check::next_routine`; `next_due` is the same without warm-ups).
  An account a check skipped for its own reasons (its lock busy, a check of it still running) counts as tried, so the others are not starved.
- When the user asks: `cc-rotate-ctl check [<account>...]`, or **Check usage** in the app, which ignore `not_before` and also check paused accounts; with `usage_checks false` they still run, the automatic ones do not.
- `cc-rotate-ctl check` and the app at start first settle every scratch profile left behind (`usage_check::sweep`).

### 20.3 A check that dies or is interrupted

Claude Code may have renewed the login in the scratch profile, retiring the stored refresh token, when the check dies before step 7 commits or is killed at its time limit, and the renewal may be lost with it (killed before it wrote the new login).

- A scratch profile left behind always means the check did not store its outcome. The next holder of the account's lock (a check or a swap of that account, or the sweep at app start) settles it:
  - `start.fp` is written before the login: without it, or with a fingerprint other than the stored login's (a re-login since), the leftover is stale and deleted unread;
  - a renewed login in it is stored, and a blanked one marks the account `needs_login`;
  - anything else (the login unchanged, none left) leaves the doubt, and the account is held back;
  - a login that cannot be read is kept, with the account held back and counting as busy, for an hour in case it becomes readable (a locked Keychain, a file another program holds), then given up the same way.
- A check records its Claude Code's process id with its start time (`claude.pid`); while that process runs (on Unix, while any process of its process group runs, since what it started outlives it), its scratch profile is left alone and the account counts as busy (a swap passes over it). A reused process id has another start time and does not count.
- After a check, a timeout, an error while waiting for Claude Code (which then is killed), or no login left at all hold the account back too.
- A held-back account is not picked, not swapped to by hand, and its next check (5 minutes after a failure, respecting the usage endpoint's wait) makes Claude Code renew (20.1, step 3), which settles it either way.
- A fresh login of the account clears its check state and deletes its leftovers; removing an account takes its lock and deletes its scratch profiles and check state.

### 20.4 Confirming the account in use

A threshold swap whose trigger is a status line reading with a window over its threshold whose reset time is not known to be the account's own, or is another account's too (section 8), first reads the account in use's usage (`usage_check::confirm_active`), within the swap's 25 s budget for checks.
It uses a copy of the profile's login with the refresh token removed, so Claude Code cannot renew (and so retire) the login the profile's sessions use; when the access token expires within two minutes, there is no confirmation.
The scratch profile is `<data dir>/staging/confirm-<uuid>/`, never recovered and deleted afterwards (and by the sweep).
A reading stamped with the account becomes its sample (`profile = check`) and its reset times its own; when the account is below its thresholds by it, the swap is skipped.
When the confirmation cannot be made (rate limited, no access token, an error), the swap goes ahead as the reading says, as before.

The status line also asks for a confirmation in the background (`cc-rotate-ctl confirm-active`) when readings it drops as another account's are at a limit while no reading of the account in use arrived for 10 minutes, so wrong reset times cannot hide a used-up account: the first such reading since the account became active asks at once, copy or not (at a limit, a genuine reading can repeat another account's exactly, both at 100% with the same reset time); after that, a reading asks only when it is not an exact copy of another account's latest (a session idle since an earlier swap repeats it for as long as it idles) and no reading of the account in use came for 10 minutes, at most every 10 minutes. One of the sessions ticking at once asks.

### 20.5 Identifying a changed login

A login that changed in the profile without cc-rotate writing it, and that `.claude.json` does not reveal as a `/login` (section 8, step 3), is identified before it is stored (`swap::identify_changed_login`).
Claude Code is asked whose it is the way a stopped swap's login is (section 6): with a copy whose refresh token is removed, in a scratch profile, matching the account id or else the email, and the organization where both are known.

- The active account's login (a renewal) is stored as its login.
- Another pool account's login (a `/login` of an account `.claude.json` already named, from before a swap) makes that account active with it; the account that was active keeps its own stored login.
- Any other account's login marks the profile foreign, so it is never stored.

It runs with the swap lock, at most once a minute: started in the background by a status line tick (`cc-rotate-ctl settle-login`), by the app on its own thread, or by `cc-rotate-ctl status`.
A swap identifies first, so it never stores another account's login as the outgoing account's; when the profile's login changed again, unseen, by the time it holds Claude Code's locks (it may have checked accounts meanwhile), it skips, and the next request identifies that login first.
A re-login of the active account stores its fresh login again under the swap lock as it writes it into the profile, so an identification running meanwhile cannot leave the store with the profile's previous login.
While Claude Code cannot say (the access token expires within two minutes, Claude Code fails, no network), the login is not stored and no swap runs.
That lasts at most 10 minutes: then the login is stored as the active account's, as before logins were identified, and an `error` event says so, so a Claude Code that cannot identify logins never stops the rotation; `doctor` warns from two minutes on.
It is a routine run of Claude Code like a check, so it follows the `usage_checks` setting and stops with checks (20.2); on macOS it also needs a Keychain that can be used. Otherwise (checks off or stopped, or the Keychain locked) a changed login is stored as the active account's at once, as before.

## 21. Sessions stopped at a usage limit

A turn that reaches a usage limit stops, and a swap does not reach it: the session holds the login its request was built with (F11) and sits until that account resets, when Claude Code continues it (F20), or until the user types.
Overnight, that wastes hours while other accounts have room.
Normally cc-rotate swaps at 98% and a session never reaches a limit; it does when one turn takes the account past its last 2%, when the account was used up where cc-rotate could not see it, and when every account is at a limit.

### 21.1 The hook

`cc-rotate-ctl hook stop-failure` runs for `rate_limit` in the background (`asyncRewake`, F21) with a 24-hour timeout.

1. It records the stop in `waiting_sessions`: the session, when it stopped, the account whose limit stopped it, and the hook's process id with its start time; a `session` event (`waiting`) says so.
   That account is the one in the profile, unless a swap from another account landed on it at most 2 minutes before the stop: then the turn's request still carried the previous account's login, and the stop is the previous account's (a first activation, from no account, does not count, and neither does an account removed since).
   A later stop of the same session replaces the row, and the hook that recorded the earlier one exits.
   When the stop cannot be recorded (a store that stays busy), it still asks for the swap, and exits.
2. When it can wake the session at once (a swap landed just before the stop, so the profile already moved on), it does, and asks for no swap.
   Otherwise it waits up to 5 seconds for the status line to record the reading of the stop, decides again, and unless it can wake the session then, asks for a swap from it (trigger 2 in section 6).
   The reading of the stop is the first reading of the account in the profile at a limit from 30 seconds before the stop to 2 minutes after, the session's own when it has one there; other sessions' idle readings, which repeat numbers from before the limit, do not count.
   A reading recorded after the swap would be taken for a stale one of the account left and dropped, and the account would look as if it still had room.
3. Every 3 seconds it decides again (21.2); a store error, also one while recording a wake, only means it looks again later.
   To wake the session, it records the wake (a `session` event, `woken`) and exits with code 2, with a message on stderr that names the account and mirrors Claude Code's own (F20): "Continue the task you were working on when the limit was reached; do not repeat work that is already complete."
4. It stops waiting without waking the session when the session is closed, when the session is working again (21.3), when a later stop replaced it, or after 23 hours 59 minutes.
   The session is closed when the processes the hook watches are gone: the shell Claude Code runs it in and Claude Code, or Claude Code alone when the hook's parent is no shell (a shell that runs one command often replaces itself with it), recorded when it started (F21).
   A hook that found none of them stops waiting after 6 hours.
5. Without a session id it only asks for the swap, as before.

### 21.2 When to wake

The session is woken on the account in the profile when it has room by cc-rotate's readings and the profile moved on since the stop: the account is not the one whose limit stopped the turn (21.1), or a swap since the stop put it back (a swap only picks an account with room).
On the account the turn stopped on, other sessions' readings never count as room: an idle session repeats its numbers from before the limit with a fresh time.
Once the limit that stopped the turn resets, Claude Code continues the session itself (F20), and the status line then sees it working (21.3); when the user turned `autoContinueAtUsageLimit` off, cc-rotate wakes it then instead, once the reading of the stop (21.1) has reset, with a message that says the limit reset.
A session is never woken twice on the same account while it keeps stopping: every account it was woken on is kept with each new stop that comes within 30 minutes of the last wake, unless the session was seen working since.
A wake on an account that turns out to be at its limit costs one refused request, and the next stop asks for a swap, so wrong readings cannot make it loop.

### 21.3 Following up

- The status line marks a stopped session `resumed` (a `session` event) when the session reports a reading, after the stop (or after its wake), that has room now and had room at the stop (or the wake): it was woken, or continued by itself (Claude Code's own continue, or the user typing).
  A refused request's reading is at the limit, and a session idling at a limit repeats its reading, which shows room once the limit's reset time passes but not at the stop, and carries a window that had reset before the stop or wake, which a fresh response never reports; neither counts.
- `health::scan`, which the app runs every 30 seconds and status line ticks at most once a minute, marks a woken session that has reported nothing for 3 minutes `stuck` and logs `session_stuck`, which the app turns into a notification naming the account, and the Claude Code version when it was not tested.
  It marks a stop whose hook is gone without a wake `ended`.
- Every change of a stop's state applies only from the state its writer read, so concurrent scans, hooks and status lines never undo each other or notify twice.
- Rows are dropped 7 days after their last change.
- `status` and the app's overview count sessions waiting at a limit.

The same scan warns before sign-ins end: a sign-in lasts a fixed time (F22), so once one ends within `login_warning_days` it logs `login_expiring` once per sign-in, which the app shows as a notification and a banner with a button to sign in again; `status` and the account's row say when.
An account not in use whose sign-in ended and whose access token expired with it is marked `needs_login` with a `dead_login` event (`sign_in_ended`), so no swap lands on a login that cannot work.
The account in use is left to its sessions: Claude Code's renewal fails, and the status line reports the dead login.
The status line also records the Claude Code version its sessions run (F23); a version not seen before logs `claude_version`, with whether this release was tested with it.

### 21.4 Testing

Unit and integration tests cover the decision (`tests/waiting.rs`), the scan, and the hook process waking a session once its swap lands (`ccr-cli/tests/stop_failure.rs`, including a second stop just after a swap waking at once without another swap).
`tests/e2e/wait-at-limit.py` runs the real, interactive Claude Code in a pseudo-terminal against a fake Messages API (`tests/e2e/fake-api.mjs`), in a scratch store and profile that the checkout's own `cc-rotate-ctl setup` creates, with two accounts copied from the real store with dummy refresh tokens (`examples/e2e_stage.rs`), so nothing can renew a real login and no quota is used.
It passes when the session stops at the first account's limit, the hook swaps and wakes it, and it continues on the second; with `--closed`, both accounts are at their limit, and it passes when the session is woken at most once per account and the hook stops waiting once the session is closed.

## 22. Value and extra usage

### 22.1 What use is worth at API prices

The status line input carries `cost.total_cost_usd`: what the session's use so far would cost at API prices, as Claude Code estimates it (what `/cost` shows), and `cost.total_duration_ms`, the wall time its process has run.
Claude Code restores both from the session's saved state on `--resume`, and a fork starts with the total of the session it forked; `/clear` starts a new session at $0, and `/login` resets the total.
The status line runs as a session starts, at $0.

Every tick, in the rotation profile (also while a stopped swap is being settled, for the account in use) and in observe mode, counts what that total added since the last tick of the same process for the account the requests went to, in hourly buckets (`account_costs`).
`session_costs` holds the last total per session and Claude Code process (`session_processes`, section 5), since two processes can run one session (resumed twice, each restoring the same total).
The account is:

- in the rotation profile, the account in use, unless the tick's reading is another account's: a reading the session has shown unchanged since before the account in use became active (section 8, step 2) counts for the account whose latest reading it repeats exactly, else the one sharing the most windows' reset times with it, else the account the last swap left; a stale reading counts for the account the last swap left, and one attributed elsewhere (section 8) for the account whose latest reading it repeats exactly, else the one sharing the most windows' reset times with it, else the account the last swap left; the request still carried that account's login;
- in observe mode, the profile's account.

A process's first total counts whole only when its session was never seen and has run under a minute (`total_duration_ms`); otherwise it is only where counting starts, since the process carries what the session spent before (resumed or forked, with the total and run time it had, or running before cc-rotate counted).
A total below the last one (`/login`) is also only where counting goes on from.
`history` sums the buckets per calendar week (`api_value_usd`); `cc-rotate-ctl report` prints the current week and the period, and the app's account page the last 4 weeks.
The app's **API cost** chart (section 11) shows the buckets themselves, per hour over the last 24 hours and per day over the last 7, stacked per account.
These tables, with `session_processes` and `session_readings`, are pruned with the samples (`sample_retention_days`).
Removing an account removes its `account_costs` rows with it, so its past API value is gone from the report and the charts.

### 22.2 Extra usage

A usage report's `extra_usage` (F17's body) has `is_enabled` (false while extra usage cannot cover requests: off, or its monthly limit reached), `monthly_limit`, `used_credits` and `utilization`, amounts in minor units of `currency` (cents for USD), as Claude Code's own schema documents.
Every report cc-rotate reads (a usage check, a confirmation, another profile's cache, sections 9.1 and 20) records it per account (`extra_usage`), a newer one replacing an older one.
`status`, the snapshot and the account page show it.

The account in use runs on paid extra usage when the scheduler picks no other account, a limit that applies to it is used up (at 99.5% or more, not merely past cc-rotate's threshold), and its latest report says extra usage is on.
That report can be old, since the account in use is only read by a confirmation (section 20.4): when it is older than `usage_check_max_age_s`, the status line asks for a confirmation (at most every 10 minutes, with usage checks on) in place of a swap that has nowhere to go, though never of a swap away from paying, and the warning says when it was read.
`extra_usage::scan`, part of `health::scan`, logs `paid_usage` once per such episode, with the spend so far, which the app shows as a notification; while a swap away from it is due (below) it waits up to 2 minutes from when that account began paying for the swap to end the episode, then warns that the swap did not land. The episode ends when an account has room again or the account in use has extra usage off.
With `avoid_extra_usage` on, the status line tick and the app's sync then ask for a swap (`avoid_extra_usage`) to the parked account, not held back, whose latest report says extra usage is off, the one that frees up first, ahead of any other decision but a dead login, and at most every 30 seconds.
Its sessions stop at the limit and continue once an account has room (section 21).
An account whose extra usage was never read is not taken for one without it.

## 23. Keeping 5-hour windows running

A 5-hour window starts at an account's first request, rounded down to 10 minutes, and resets 5 hours later (section 7.2).
An account with no window running starts its 5 hours only when rotation reaches it, so it is ready again later than it would be with a window that started earlier.
For accounts the user opted in (`keep_running` on `accounts`, schema 8, off by default; the account page, `cc-rotate-ctl keep-running`), the app starts the next window as soon as the last one ends while the account is not in use.
Simulated over 28 days of bursty use, starting every account's window at its reset served as much as a schedule that knew the future, 1 to 7 points more of the demand than letting windows start with use, and only when demand exceeded what the accounts give; with room to spare it changes nothing.
Running windows go first in the pick order (section 7.2), so these accounts are used first.

### 23.1 One warm-up

A warm-up (`usage_check::warm_up`) is a usage check (20.1) with one more run before `/usage`, in the same scratch profile, under the same account lock, so whatever either run renews is handled as a check handles it:

1. `claude -p "Reply with the single word OK." --model haiku --tools "" --strict-mcp-config --no-session-persistence --output-format json --debug-file <scratch>/warm-debug.log`, in the environment of 20.1, step 4, with its output in `warm-out.json` and `warm-err.log`.
   Measured on 2026-10-25 (Claude Code 2.1.310): one turn of `claude-haiku-5-5`, 4 output tokens and about 4,500 cache-creation tokens of system prompt, $0.0009 at API prices, and it starts the window.
2. Then `/usage`, as in 20.1, so the new window shows; only a reading fetched after the prompt counts.
   While `not_before` runs (the usage endpoint's `retry-after`, or the back-off after a failed reading), this run is left out (R17), and the outcome says when the next reading is due.
   Should the prompt run's debug log show the usage endpoint refusing, its wait is kept as well.

The prompt's JSON result decides what happened:

- Another model in `modelUsage`, more than one turn, or `total_cost_usd` above `WARM_MAX_COST_USD` ($0.02): it did not do what was asked.
  Warm-ups stop (`warm_ups_blocked` in `meta`, an `error` event) until the user starts them again: **Start again** on an opted-in account's page, which says why they stopped, or turning `keep_running` on for an account; the window it started still counts.
- An error result or no turn: it did not go through (the account at a limit, a network or login problem), and `warm_problem` says why.
- Otherwise it went through: `warmed_at` (the time the prompt returned, so a window it started is never thought to end early) is recorded and a `warm_up` event (routine in the activity list) carries the cost.
- `claude` not found counts as not going through, so it is retried later rather than every minute.

This is recorded even when the login Claude Code left cannot be read.
A run that times out may have renewed the login, so the account is held back as in 20.3.
A warm-up holds the account's lock for up to two runs (`JOB_TIMEOUT`), so a re-login and removing an account wait that long for one to finish.
`describe_warm_up` and `cc-rotate-ctl warm-up <account>` (which runs one now, whether or not the account is opted in) report it.

### 23.2 When warm-ups run

The app's background job (20.2) runs a warm-up for the first account in pick order (`usage_check::next_warm_up`) that is:

- opted in, parked, and not held back;
- kept out of use by no window but the 5-hour one (a weekly or other limit makes a window pointless);
- without a running 5-hour window by its latest reading (`Candidate::session_running`), and without one a warm-up started (`warmed_at` rounded down to 10 minutes, plus 5 hours, is in the past), since the reading after a warm-up can be refused (F17); a reading newer than the warm-up that shows a window running since it decides instead, since the prompt may have landed in a window that was already running (a reading without one may lag behind the request);
- not tried in the last 15 minutes (`warm_attempt_at`), including a warm-up that could not run (its lock busy, its login unreadable or in the profile, a swap unfinished), so the background moves on to other work.

Warm-ups need usage checks on and possible (20.2), since they run the same way, and stop while either is not.
Only the account in use is never warmed: it starts its own window as it is used.

### 23.3 Elsewhere

- While warm-ups run (`usage_check::warm_ups_paused` says none of them is stopped), the forecast (7.5) gives an opted-in account that is not in use or held back a new window as soon as its window ends, and one at once when none runs.
- `doctor` lists the opted-in accounts, when a warm-up last started a window, and warns while warm-ups are stopped or paused (usage checks off or stopped), and for an account whose last warm-up, in the last 6 hours, did not go through.
- The account page shows when a warm-up last started the account's window, or why the last one in the last 6 hours failed, and why warm-ups are stopped or paused.
- The forecast leaves out an account another limit keeps out of use, as warm-ups do; it cannot tell whether the app runs.
