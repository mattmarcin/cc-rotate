# cc-rotate: one Claude Code profile, a pool of accounts

Status: draft for review, 2026-10-24.
Tested against Claude Code 2.1.310 on Windows 11 (native install).
Linux behavior was read from the 2.1.310 linux-x64 build and runs the Windows code paths unchanged; verified with real accounts in WSL.
macOS behavior was read from the 2.1.310 darwin-arm64 build (section 18) and verified with real accounts on a Mac: swaps through the Keychain in a desktop session and through the file over SSH, a renewal during a usage check, and identifying a changed login.

## 1. Goal

Run all Claude Code CLI work under a single profile so every session can see and message every other session, while a pool of the user's own Claude subscription accounts backs that profile.
When the active account nears any of its usage limits, the profile switches to another account in place, and running sessions continue on their next request with no restart and no proxy.
Accounts are used in an order the user sets, accounts without a weekly limit first, and rotation switches back to a better ranked account once it is usable again.
A local dashboard shows every account, its live and historical usage, and how rotation is spreading load, and it runs the official Claude login for any account that needs one.

## 2. Non-goals

- No HTTP proxy, no `ANTHROPIC_BASE_URL` override, no modification of the Claude Code binary.
- cc-rotate never calls Anthropic APIs itself: no token refresh, no usage requests of its own.
  All Anthropic traffic is Claude Code's own; a usage check (section 20) runs Claude Code's `/usage`, and a login renewed during one was renewed by Claude Code.
- The Claude desktop app is out of scope.
  It injects its own token through environment variables and owns refresh, and Claude Code prefers an injected token over `.credentials.json`, so a file swap cannot reach it.
- Profiles the user already has (for example one `CLAUDE_CONFIG_DIR` per account) are not changed, except for the opt-in usage reporting in section 9.

## 3. What Claude Code already does (research findings)

These behaviors were read from the 2.1.310 bundle.
They are undocumented internals, so section 12 turns each one into an end-to-end acceptance test, and `cc-rotate-ctl doctor` warns on any untested Claude Code version.

| # | Behavior | Why it matters |
|---|---|---|
| F1 | Before using its token, each session stats `<profile>\.credentials.json`; if the mtime changed it drops the in-memory credential and re-reads the file. The 30 s figure is the read-cache TTL, which an mtime change bypasses. | A swap reaches every running session on its next API request. |
| F2 | On a credentials change, an "adopt sibling login" path re-runs account-dependent setup (managed settings, claude.ai connectors). | Claude Code itself expects another process to change the login under it. |
| F3 | Saving a refreshed token is compare-and-swap: it writes only if the on-disk `refreshToken` still equals the one it sent; otherwise it adopts the newer on-disk login. | A session still on account A never overwrites a swap to B. |
| F4 | Refresh runs under two lock directories with proper-lockfile semantics: `<profile>\.oauth_refresh.lock` and the legacy `<profile>.lock` (stale after 60000 ms, mtime updated every 5000 ms). After acquiring, it re-reads the file and refreshes whatever is on disk. | cc-rotate can exclude refreshes during a swap by holding the same locks. |
| F5 | The rate-limit tracker has an account epoch: on account change it clears utilization state and drops responses tagged with the previous epoch. | After a swap, the statusline stops reporting the old account's percentages. |
| F6 | Statusline input carries `rate_limits.five_hour` and `rate_limits.seven_day`, each with `used_percentage` and `resets_at` (epoch seconds), plus `session_id`. The statusline runs after every assistant message, and also every `refreshInterval` seconds (the setting is in seconds). | Usage samples and the swap trigger cost nothing extra; a session still showing an earlier account can be recognized (section 8). |
| F7 | The `StopFailure` hook receives `error` from a fixed set that includes `rate_limit`. | Backstop trigger when a turn stops at the limit. |
| F8 | When the account's login is rejected (`invalid_grant`), Claude Code blanks `refreshToken`, `accessToken` and `expiresAt` in the file. | Detects a dead login. |
| F9 | `claude auth login --claudeai [--email <e>]` runs without a TTY: it prints a sign-in URL, opens the browser, completes through a localhost callback, and also accepts a pasted code on stdin. `CLAUDE_CONFIG_DIR` points it at any directory. | The dashboard can run the official login flow and capture its result. |
| F10 | `.credentials.json` holds `claudeAiOauth` (the account login) and `mcpOAuth` (MCP server logins) side by side. | A swap must replace only `claudeAiOauth`. |
| F12 | Every read-modify-write of the credentials document (a refresh's save, an MCP login, a logout) runs under a third proper-lockfile lock, `<profile>/.storage-write.lock` (`realpath: false`, stale after 15000 ms, 10 retries). | A swap holds it too, so no such write can put the outgoing login back after the swap wrote the target. |
| F13 | The rate-limit tracker keeps one entry per window the API reports in its headers (`five_hour`, `seven_day`, `seven_day_overage_included`, `overage`), present while the API reports it and its reset has not passed. The statusline's `rate_limits` exposes `five_hour` and `seven_day` (plus `spend_limit` behind a gateway), and the input carries `model.id`. `/usage` groups its `limits[]` rows by kind: `session`, `weekly_all`, `weekly_scoped` (with a model scope). | cc-rotate records every window the statusline reports, by name, so a window Claude Code adds later needs no code change; model-scoped windows apply by `model.id`. |
| F14 | Claude Code caches `/usage` results in the profile's `.claude.json` as `cachedUsageUtilization`, stamped with the `oauthAccount.accountUuid` read before the fetch. A credentials change (a cc-rotate swap) does not update `oauthAccount`, so after a swap the cache holds the new account's usage under the old account's id (observed: a Team seat's usage, without `seven_day`, stamped with a Max account's id two minutes after a swap). Token renewals also merge the new account's profile fields (`seatTier`) into the old `oauthAccount`. | cc-rotate does not use the rotation profile's `cachedUsageUtilization` or `oauthAccount` for usage or plans: neither can be attributed to an account reliably. |
| F16 | In a profile whose login never changes account, the `cachedUsageUtilization` stamp is reliable: Claude Code writes the cache only when the profile's `oauthAccount.accountUuid` is still the one it read before the fetch, and drops a cache stamped with another account when it reads it. The cache is `{fetchedAtMs, accountUuid, utilization}`, where `utilization` is the `GET /api/oauth/usage` body: one field per limit system (`five_hour`, `seven_day`, `seven_day_opus`, many codenamed ones, mostly null) and `limits[]`, the rows `/usage` shows (`kind`, `percent`, `resets_at` as RFC 3339, optional `scope.model` or `scope.surface`). Sessions refresh it when they read usage, for example for `/usage` and at a limit (observed: a profile with an agent at its 5-hour limit held a reading 6 minutes old). | The user's other profiles tell cc-rotate when an account was used up outside the pool (section 9.1). |
| F15 | Every login (`claudeAiOauth`) carries `subscriptionType` (`max`, `team`, `pro`, `enterprise`) and `rateLimitTier` (`default_claude_max_5x`, ...), and renewals repeat them. Claude Code treats `team` with `default_claude_max_5x` as a premium Team seat. | Plans ("Max 5x", "Team 5x") are derived from the login itself, which travels with the account. |
| F17 | `/usage` runs without a session (`claude -p /usage`, `supportsNonInteractive`): zero turns, zero tokens. With a claude.ai login holding the `user:profile` scope it fetches `GET /api/oauth/usage` (renewing the login first when its access token expired, `refreshOAuth: true`) and caches the body in the profile's `.claude.json` (F16); a login injected with `CLAUDE_CODE_OAUTH_TOKEN` is treated as an API token and fetches nothing. The endpoint is rate limited per login: a 429 carries `retry-after`, which Claude Code holds in memory (capped at 1 h, 5 min without the header) and logs as `429 remembered for this bearer; not asking again for <n>s`. A run takes about 2 to 4 s. | cc-rotate reads accounts that are not in use with Claude Code's own request and no quota (section 20). |
| F11 | On a quota 429 for the 5-hour or weekly window, the request does not fail: it sleeps until the reset and sends "usage limit recheck" probes with the current credentials; an admitted probe resends the request at once. Recheck cadence was not determined from the bundle. | A turn that hits the wall resumes on its own once a swap lands, and the turn may never stop, so `StopFailure` may not fire. |

Prior art (claude-account, clauth, claude-auth) swaps credential files between sessions, with no lock coordination with Claude Code's refresh and no live swap.
The claude-account README independently confirms the refresh-token rotation hazard that section 6 addresses.

## 4. Architecture

```
            ┌──────────────── profile  ~/.claude-rotate ─────────────────────────┐
 user  ──►  │ claude (session 1..n)        .credentials.json  (active login)     │
            │   statusLine ─► cc-rotate-ctl statusline ─┐                        │
            │   StopFailure ─► cc-rotate-ctl hook ──────┤                        │
            └───────────────────────────────────────────┼────────────────────────┘
                                                        ▼
                 ccr-core (Rust): store · lock · credfile · scheduler · login
                                                        ▲
            cc-rotate app (Tauri 2: window + tray) ─────┘   reads/writes the same store
            <data dir>/store.db  (SQLite, WAL)
```

A Rust Cargo workspace with three members:

- `crates/ccr-core`: the library every entry point uses.
- `crates/ccr-cli`: the `cc-rotate-ctl` binary (statusline, hook, swap, login, status, doctor, setup) and the `cc-rotate` launcher.
- `app/src-tauri`: the `cc-rotate-app` Tauri 2 desktop app (dashboard window, tray icon, native notifications), with its UI in `app/src` (TypeScript, Vite, uPlot).

Rotation depends only on `cc-rotate-ctl`, never on the app running.
The app is the only place native notifications come from, so it registers itself to start at login.

### 4.1 Components

- **store**: SQLite schema, migrations, and transactions over `rusqlite` with bundled SQLite.
- **lock**: acquires and releases Claude Code's two refresh locks with matching semantics, plus cc-rotate's own swap lock.
- **credfile**: reads and atomically writes `.credentials.json`, touching only `claudeAiOauth`.
- **scheduler**: decides whether to swap and to which account.
- **sampler**: turns statusline input into usage samples and keeps the store current (write-back).
- **login**: runs `claude auth login` in a staging directory and imports the result.
- **app**: Tauri commands over ccr-core, a 1 s poll of SQLite `PRAGMA data_version` that pushes a change event to the UI, the tray, and notifications.

### 4.2 Files and names

| Item | Value |
|---|---|
| Profile directory | `~/.claude-rotate` (override with `--profile`) |
| Launcher | `cc-rotate`, an executable next to the CLI (section 4.4) |
| Control CLI | `cc-rotate-ctl`, installed to `~/.local/bin` by default |
| Desktop app | `cc-rotate-app`, installed next to the CLI |
| Data dir | `%LOCALAPPDATA%\cc-rotate` on Windows, `~/.local/share/cc-rotate` on Linux, `~/Library/Application Support/cc-rotate` on macOS (override with `CC_ROTATE_DATA_DIR`) |
| Store | `<data dir>/store.db`, with its key in `<data dir>/master.key` |
| Login staging | `<data dir>/staging/<uuid>/` |
| Usage check scratch profiles | `<data dir>/staging/check-<account id>-<start ms>-<uuid>/` |
| Account locks | `<data dir>/locks/account-<id>.lock` |
| Logs | `<data dir>/logs/` |

### 4.3 Profile setup

`cc-rotate-ctl setup [--from <template profile>] [--profile <dir>] [--remove-alias] [--keep-existing]` creates the rotation profile so a new user does not hand-edit anything.
The template defaults to `~/.claude`.

- Copies `settings.json`, `settings.local.json`, `keybindings.json`, and the `agents`, `commands`, `hooks`, `skills` and `plugins` directories when present, rewriting every occurrence of the template's path to the new profile's path in copied JSON (hook commands and plugin install paths reference their own profile).
- Links `CLAUDE.md` with a hard link when both profiles are on one volume, else copies it.
- In the new `settings.json`, records the template's `statusLine.command` as `statusline_downstream`, sets `statusLine` to `cc-rotate-ctl statusline` with `refreshInterval` 30 (seconds), and appends a `StopFailure` hook running `cc-rotate-ctl hook stop-failure`.
- Appends a `SessionStart` hook running `cc-rotate-ctl hook session-start` for herdr (section 19).
  For each hook event it first drops only the groups that run `cc-rotate-ctl`, so the user's own hooks and herdr's stay, and `--force` never duplicates cc-rotate's.
- Merges into `.claude.json` from the template: onboarding flags (so the first launch skips onboarding), user-level `mcpServers`, and per-project trust flags and MCP settings (`mcpServers`, `enabledMcpjsonServers`, `disabledMcpjsonServers`, `disabledMcpServers`).
  Values already in the profile always win, so re-running setup never undoes a change made there.
- Never copies `.credentials.json` (including MCP OAuth tokens, which each profile signs in to once with `/mcp`), the template's account data, history, project transcripts, or sessions.
- Refuses to overwrite an existing profile unless `--force` is given, and `--force` still keeps an existing `.credentials.json`.
  With `--keep-existing` it leaves an existing profile as it is and succeeds instead, so the installer runs setup on every upgrade and setup itself decides from the profile it resolves (the `profile_dir` setting is unset for the default profile, or when the store was created after the profile).
- The statusline and hook commands start with the `cc-rotate-ctl` path unquoted.
  On Windows, Claude Code may run them through PowerShell, cmd or Git Bash, and a quoted path followed by arguments is a PowerShell parse error, so a path with spaces uses its 8.3 short form.
  On Unix they run through a POSIX shell, so a path with spaces or other special characters is single-quoted.
- `--remove-alias` removes the `cc-rotate` PowerShell function (the block between `# >>> cc-rotate >>>` and `# <<< cc-rotate <<<`) that earlier versions added, because a PowerShell function hides an executable of the same name.
  With an existing profile and no `--force`, that is all setup does; `doctor` warns while the function is still there.

### 4.4 Launcher

`cc-rotate [args]` resolves the profile like every other entry point (`--profile` is not taken, since every argument goes to Claude Code; `CC_ROTATE_PROFILE`, then the `profile_dir` setting, then `~/.claude-rotate`), finds `claude` (the `claude_path` setting, else `PATH`), sets `CLAUDE_CONFIG_DIR` for the child only, and passes every argument through.
It is an executable rather than a shell function so it works the same in every shell, including tools that restore a session by typing `cc-rotate --resume <id>` into a fresh shell.

- On Unix it replaces itself with `claude` (`exec`), so signals and the exit code are Claude Code's own.
- On Windows it waits for `claude` and exits with its exit code.
  It registers a console control handler that ignores Ctrl+C and Ctrl+Break, so those reach Claude Code while the launcher keeps waiting; a handler, unlike the ignore flag, is not inherited by the child.
- It warns on stderr when started in the home folder, where Claude Code does not run status lines, then continues.

## 5. Store

SQLite in WAL mode with `busy_timeout` 5000 ms, since many statusline processes write at once.

- `accounts(id, label, email, account_uuid UNIQUE, org_uuid, subscription_type, rate_limit_tier, state, position, weekly_limit, added_at, last_login_at, note)`
  - `state` is one of `active`, `parked`, `needs_login`, `paused`.
  - `position` is the user's order (lower is used first); a new account goes to the end, and reordering numbers every account from 1.
  - `weekly_limit` is `auto` (detect it, section 7), `yes` or `no`.
  - `subscription_type` and `rate_limit_tier` are refreshed from every stored login (F15).
  - At most one row is `active`, enforced by a partial unique index; zero only when every account is `needs_login` or `paused`.
- `credentials(account_id PK, oauth_blob, refresh_fp, expires_at, refresh_expires_at, updated_at, source)`
  - `oauth_blob` is the `claudeAiOauth` object sealed as described in section 5.1.
  - `refresh_fp` is a SHA-256 prefix of the refresh token, so comparisons never decrypt.
  - `source` is `login`, `swap_out` or `sync`.
- `samples(id, ts, account_id, profile, session_id, model)`, indexed on `(account_id, ts)`: one reading, with the session's model when the statusline reported one.
- `sample_windows(sample_id, account_id, name, pct, resets_at)`, primary key `(sample_id, name)`, indexed on `(account_id, name, resets_at)`: every usage window of a reading, named as Claude Code names it (`five_hour`, `seven_day`, ...).
  A window the data source did not report has no row; it is never stored as 0%.
- `events(ts, kind, account_from, account_to, reason, detail_json)`, where `kind` is one of `swap`, `swap_skipped`, `login`, `sync`, `dead_login`, `pool_exhausted`, `error`.
- `settings(key, value)` holds the thresholds and options in section 13.

### 5.1 Encryption at rest

Every sealed blob is `CCR2 || nonce (24 bytes) || XChaCha20-Poly1305 ciphertext and tag`, under one random 256-bit data key with a fresh random nonce per blob.
The associated data binds a blob to its purpose: `cc-rotate/credential/v2/account:<id>` for a login, `cc-rotate/backup/v2` for a backup, so a blob moved to another row or file fails to open.

The key is `<data dir>/master.key`, 32 raw bytes, created on first use.
It is written in full to a temporary file and published with a hard link, which fails rather than replacing an existing file, so concurrent first uses agree on one key.
On Unix the file is mode 0600 and the data directory 0700; on Windows it inherits the user profile's ACL (the user, SYSTEM, Administrators).
When the key file is missing but sealed logins exist, cc-rotate reports it instead of creating a new key.

The key must be readable without any prompt: the statusline is a short-lived process that runs every few seconds per session, often headless or over SSH.
That rules out OS keyrings as the default (a locked Secret Service over SSH, Keychain access prompts for unsigned binaries whose signature changes on every build).
The key file protects against casual reads and against a copy of the store leaking on its own.
It does not protect against code running as the same user, which is the same trust level as Claude Code's own plaintext `.credentials.json`.

Schema 1 stores sealed logins with Windows DPAPI.
Opening a schema 1 store on Windows decrypts each login with DPAPI and re-seals it in the format above in the same transaction that sets `user_version` to 2, and converts the `.dpapi` backups to `.ccr`.
A login that cannot be converted is left in place, logged as an `error` event, and reading it asks for a new sign-in.
DPAPI code remains only for that conversion.

Schema 3 replaces the two fixed usage columns with `sample_windows`, in the transaction that sets `user_version` to 3.
Every sample keeps its id, and its `five_pct`/`week_pct` columns become `five_hour`/`seven_day` rows when not null.
`priority` is renamed to `position` with its values kept, so accounts that shared a priority share a place in the order until the user reorders them.

**Invariant:** the active account's newest login lives in `.credentials.json`; the store's copy of that row may lag.
Every parked account's newest login lives only in the store.
This is what makes the store the single source of truth for parked accounts without any process racing Claude Code for the active one.

## 6. Swap protocol

Triggers, in priority order:

1. A window in the active account's latest sample that applies to the model in use reaches its threshold (section 7).
2. A `StopFailure` hook with `error == "rate_limit"`.
   This is a backstop only: under F11 a turn at the wall usually sleeps instead of stopping, and trigger 1 still fires because the statusline reports 100%.
3. A dead login (F8) observed by the sampler.
4. A manual swap from the CLI or dashboard.
5. Switch back: an account that ranks strictly above the active one is usable again (section 7.2).

The statusline never performs a swap inline.
It spawns a detached `cc-rotate-ctl swap --from <account_id> --reason <r>` and returns, so the status line stays under its time budget.

Swap steps:

1. Acquire cc-rotate's swap lock (`<data dir>/swap.lock`, proper-lockfile semantics).
   If it is held, exit; another process is already swapping.
2. Re-read the store.
   If the active account is no longer `--from`, log `swap_skipped` and exit (idempotent across many sessions triggering at once).
   If the last swap was less than `swap_cooldown_s` ago and the trigger is a threshold or a switch back, log `swap_skipped` and exit, unless the trigger is a threshold and the active account arrived over its limit (section 7.2).
   For a switch back, also skip when the active account has been active for less than `switch_back_dwell_s`, or when no account ranks above it any more.
3. Record the readings the user's other profiles hold (section 9.1), then pick the target account (section 7).
   When the pick's latest reading is older than `usage_check_max_age_s` and checks are on, check it first (section 20) and pick again; at most three checks per swap, none started after 25 s.
   Then take the target's account lock (section 20), waiting for a background check of it to finish, recover what a dead check left (section 20.3), and pick again under the lock if a check that finished meanwhile found the target over a threshold, rejected or held back; an account whose lock or leftovers keep it busy is passed over.
   Before all this, a threshold swap whose reading may not be the account in use's own confirms it first (section 20.4), and is skipped when the account's own reading is below its thresholds.
   If none is eligible, log `pool_exhausted` and exit without changing anything; the app turns that event into a notification. When the only eligible accounts were passed over as busy (a check of them running), the swap is skipped instead: the pool is not exhausted.
4. Acquire `<profile>/.oauth_refresh.lock`, then `<profile>.lock`, in the same order and with the same stale and update settings as Claude Code (F4), then `<profile>/.storage-write.lock` (F12), timing out after 30 s.
   On timeout, release whatever was acquired, log `error`, and exit; the next trigger retries.
   Read everything else the commit needs, then record the swap as pending (`swap_pending` in `meta`: the target login's fingerprint, the outgoing and the target account) before writing; the status line's write-back leaves a file with that fingerprint alone, so a tick before the commit cannot store the target's login as the outgoing account's. The commit clears it, and a failed commit restores the outgoing login and clears it.
   A failed write or commit restores the outgoing login and clears the mark only when the profile verifiably has the outgoing login again; otherwise the mark stays.
   A swap that died in between (a crash, or a failure that could not be undone) leaves the mark with nobody holding the swap lock, and is settled only on certainty (`swap::finish_dead_swap`): when the profile has exactly the outgoing account's login, the write never happened and the mark is cleared; when it has exactly the target's, the swap is completed (states only; the outgoing login was stored before the write); when it verifiably has no usable login (Anthropic rejected whichever it was, or a `/logout`; on macOS only while the Keychain can be read, since a locked Keychain can hide the live login behind a stale or missing file), the outgoing account's stored login, saved before the write, is put back under Claude Code's locks and the target is held back until a check settles whether its login still works (20.3); otherwise (a renewal since, a `/login`) Claude Code is asked whose login it is, with a copy whose refresh token is removed, matching the account id or else the email, and the organization where both are known, and the swap is completed, forgotten, or the login treated as foreign accordingly.
   Until then nothing is stored from the profile, no usage check runs, a fresh login of the active account is stored but not written into the profile, and no swap runs, not even one asked for by hand: each would overwrite the only copy of a login nobody can identify, or file it under the wrong account. The sessions go on with the login the profile has. Settling is tried at most once a minute, by `cc-rotate-ctl settle-login` started in the background by a status line tick, by the app on its own thread, or by `cc-rotate-ctl status`; it needs `claude` to run and the network. After 10 minutes an `error` event, `doctor` and the app say so. (Asking the user is no way out: `/status` and `claude auth status` show the identity a swap never updates, F14.)
   A login in the profile that is not known to be the active account's (a `/login` of an account outside the pool, or one left unidentified) is never stored as the active account's by a swap.
   A fresh login of the active account is written into the profile only if that account is still the active one once a stopped swap is settled; then it ends a `/login` of an account outside the pool, and Claude Code's renewals of it are stored again.
   The write-back also re-reads the credentials' change marker before storing, so a login read before a swap's write is never stored under the account the swap made active.
5. Under the locks, read the profile's credentials (`.credentials.json`, or the Keychain item on macOS, section 18) and save its `claudeAiOauth` into the outgoing account's row (`source = swap_out`).
   If that block's refresh token is blank (F8), mark the outgoing account `needs_login` instead.
6. Decrypt the target's `claudeAiOauth`, write it into `.credentials.json` with every other key preserved, using write-to-temp then rename.
7. In one transaction, set outgoing to `parked` (or `needs_login`) and target to `active`, and log `swap` with the triggering sample's windows, the window that triggered it, and the reason the target was picked (section 7.3).
8. Release the profile locks in reverse order, then the swap lock.

Mid-turn behavior: at 98% the active turn keeps running, and its next request goes out on the target account (F1).
If a request already hit the wall before the swap, the sleeping request resumes on the target account at its next recheck probe (F11).

Why this closes the race: any refresh either finishes before step 4, so step 5 captures the rotated token, or starts after step 8, re-reads the file under the lock (F4), and refreshes the target account.
No order leaves a retired refresh token in the store.

## 7. Scheduler

### 7.1 Windows and eligibility

Each window in a sample is classified by its name:

| Name | Kind | Applies to |
|---|---|---|
| `five_hour` | 5-hour | all models |
| `seven_day` | weekly | all models |
| `seven_day_<family>`, `five_hour_<family>` (`opus`, `sonnet`, `haiku`, `fable`) | weekly or 5-hour | that model family |
| any other `seven_day_*` | weekly | all models |
| anything else | other | all models |

An all-models window always applies.
A model-scoped window applies when the rotation profile's most recent `model.id` (recorded on every tick) contains its family, and also when no model is known yet.
Unknown names count as all-models limits, so a new limit system blocks too early rather than too late.
5-hour windows use `swap_threshold_5h`, weekly windows (all-models or scoped) use `swap_threshold_7d`, and other windows the lower of the two.

An account's windows are those of its latest sample; a window the latest sample lacks is no longer reported and does not count.
A window's effective usage is its percentage, or 0 once its `resets_at` is in the past.
An account is eligible when its state is `parked` and no applicable window is at or above its threshold.
An account with no samples has no windows and is eligible.

Whether an account has a weekly limit (on all models) is detected from its recorded windows, unless `weekly_limit` overrides it:

- **Has one:** a `seven_day` (all-models weekly) window was recorded within the retention period.
- **None:** at least two distinct 5-hour windows (reset times more than an hour apart) were recorded with a reset in the last 8 days, and never a weekly one.
  A real request on a capped account reports the weekly window next to the 5-hour one, so this avoids treating a status line that ran before the first request, or an idle account after its weekly reset, as unlimited.
- **Not known yet:** otherwise.

### 7.2 Ranking and switching back

Ranking, best first:

1. With `prefer_no_weekly_limit` on: accounts without a weekly limit, then accounts not known yet, then accounts with one.
   Not known yet sits between the two because such an account may well be unlimited, but should not push out an account known to be.
2. `position`, the user's order.
3. The most room: the smallest `threshold - usage` over applicable windows, largest first (the 5-hour threshold for an account without readings), then `label`.

```
tier(a)  = expiring(a) ? 0 : 1 + (prefer_no_weekly_limit ? {none: 0, unknown: 1, has: 2}[weekly(a)] : 0)
rank(a)  = expiring(a) ? (0, weekly_reset(a)) : (tier(a), position(a))
pick     = min over eligible a != active of (rank(a), -room(a), label(a))
switch_back_target =
    if active has a blocking window: none (trigger 1 handles it)
    else min over eligible a with rank(a) < rank(active)
                         and every applicable window <= threshold - 5
         of (rank(a), -room(a), label(a))
```

An account whose weekly budget would otherwise reset unused (`expiring`, section 7.4) ranks first, the soonest reset first.

An account can be picked on a reading that is out of date, for example when an agent used it up in its own profile since.
The status line then reports it at its limit on the first request after the swap.
When every reading of the active account since it became active has a window that applies at or above its threshold, the account arrived over its limit, and the threshold trigger skips `swap_cooldown_s` (the 30 s spacing of requests still applies).
This cannot ping-pong: the account it leaves was itself over a threshold, or ranked below it.
Readings that belong to an earlier account are not recorded (section 8, step 2), and a reading that shares a reset time with another account's latest reading does not count as proof either.
Leaving out a genuine reading here only means the cooldown applies as usual.
The swap event records `arrived_over_limit`.

A tick requests a switch back when `switch_back_target` exists, the active account has been active for at least `switch_back_dwell_s`, and the threshold-trigger throttling allows it (no request in the last 30 s, `swap_cooldown_s` since the last swap).
It is logged as a swap with reason `preferred_available`.
Room is not part of `rank`, so accounts in the same place never swap just to balance usage.
The 5-point margin keeps the target from being left again moments later; together with the dwell and cooldown this rules out ping-pong, since an account left at a threshold stays above it until its window resets.
The active account's start is recorded on every swap and adopted login (`active_since`).

Parked accounts have no live samples, which is fine: their last sample plus `resets_at` gives an exact lower bound, and the store never needs to poll Anthropic.
Usage reported by the legacy profiles (section 9) feeds the same numbers, so an account busy in another profile is not chosen blindly.

### 7.3 Explaining picks

The snapshot lists every account in pick order with a short reason ("no weekly limit, 2nd in your order"; "5-hour limit at 99%, resets in 2h 10m"; "paused"), and the next pick with its reason.
`cc-rotate-ctl next [--explain]` prints them, the dashboard shows "Next: <label> - <reason>", and swap events record the target's reason (`pick`) and, for a switch back, why it ranks above the outgoing account (`why`).

### 7.4 Weekly budget that would reset unused

What an account with a weekly limit has not used at its weekly reset is lost, and it can only be used as fast as its 5-hour windows let it, while the user works.
So an account moves ahead (`budget::expiring`) once its budget would not fit in the time left otherwise, and not before: until then it stays in reserve for when every other account is at a limit.
`use_expiring_weekly` (on by default) turns this on.

Per account with a weekly limit on all models, parked or active, whose weekly window has not reset:

- `left = max(0, weekly threshold - weekly usage)`, the weekly threshold being `min(swap_threshold_7d, weekly_cap)`; below 5 points it is not worth a swap.
- `per_hour = weekly_per_5h * min(five_per_hour, swap_threshold_5h / 5)`: weekly points an hour of use spends, at the account's pace and never faster than its 5-hour window lets through.
- `hours = left / per_hour`.

The accounts are taken in the order their weekly windows reset, since one account is in use at a time and an earlier reset must be met first.
For each, `needed` is the sum of `hours` of it and every account resetting before it, and `available` the working hours expected before its reset.
It moves ahead when `needed / available >= 0.75`; the account in use stays ahead while the share is at least 0.3, so that its own spending, which lowers the share, does not make it leave and come back.
An account that has moved ahead is used whenever it is below its limits; a 5-hour limit sends the pool to the next account as usual, and the account is taken back (switch back, section 7.2) once its 5-hour window resets.

Three rates come from the last 28 days of readings (cached for 10 minutes, so the status line stays fast), each mixed with a cautious guess that the readings outweigh as they accumulate:

| Rate | From readings | Guess, and its weight |
|---|---|---|
| `weekly_per_5h`: weekly points per 5-hour point, per account | the growth of the weekly window over the growth of the 5-hour window, between consecutive readings of the same two windows | 0.1 (a full 5-hour window is a tenth of the week), worth 50 five-hour points |
| `five_per_hour`: 5-hour points per hour of use, per account | 5-hour growth over the time between consecutive readings of the same window that grew, at most 20 minutes apart | 10, worth 2 hours |
| activity: the chance of working in each hour of the week | in how many of the weeks seen any account's 5-hour window grew in that hour | 10/24 (10 hours a day), worth 1 week |

The guesses err early: a cheaper window and a slower pace mean more hours needed.
The ranking reason says "weekly budget expires in 1d 4h with 45% left".

`weekly_cap` (per account, `cc-rotate-ctl weekly-cap`, the More dialog) lowers that account's weekly threshold below `swap_threshold_7d`, so rotation stops using it there and leaves the rest of its week to the user; budgets are counted up to it.

## 8. Write-back and the statusline

The profile's `statusLine.command` is `cc-rotate-ctl statusline`, with `refreshInterval` 30 (seconds); it also runs after every assistant message.
The desktop app runs the write-back step (step 3) and triggers 3 and 5 every 5 s as well, so the store stays current and switching back happens when only non-interactive sessions run.
Each tick:

1. Parse stdin JSON.
2. Record `model.id`, if present, as the profile's most recent model.
   If `rate_limits` has any window with a `used_percentage`, insert a sample for the active account with every such window.
   Discard it if any window's `resets_at` equals one of the outgoing account's recorded reset times within 120 s of a swap, as a guard on F5.
   Swaps within 120 s of each other add the outgoing account's reset times to the ones already recorded, so a session idle since two swaps ago is recognized too.
   Beyond those 120 s: a session only notices a new login when it next starts a request (F1), so it keeps reporting the account it used before while it idles, and when a request it started before the swap finishes afterwards (bringing that account's latest usage).
   Such a reading carries the earlier account's reset times. cc-rotate keeps, per account, the reset times known to be its own (`own_resets:<id>` in `meta`, only those still ahead counting): from readings clearly its own, from other profiles signed in to it (section 9.1) and observe mode, and from usage checks (section 20), including the one a swap usually just made of its target.
   Reset times within a minute of each other count as the same, since the status line and `/usage` may round differently.
   A reading is the active account's own when it shares no reset time with another account's latest reading, or has one of the known ones; it belongs elsewhere, and is discarded, when it shares another account's reset time and the known ones differ; otherwise it is ambiguous.
   When its reset time is both another account's and a known one (aligned reset times), the values decide: a reading that repeats another account's latest reading exactly (windows, reset times, percentages within half a point), and is not the active account's latest, belongs elsewhere, since that is what a session still showing that account reports.
   Reset times are aligned to round times, so two accounts' windows can reset at the same moment and status line data alone cannot always tell them apart.
   An ambiguous reading is recorded, since hiding a genuine reading of a used-up account would leave its sessions waiting at the limit, but it does not add to the known reset times, so a stale reading that got through never vouches for the next one; and a threshold swap that rests on one first confirms the active account's usage with a usage check (section 20).
3. If the profile's credentials changed since the last sync (a fingerprint of `.credentials.json`, or of the Keychain item on macOS; not the file's modification time, which Windows stamps from a clock that advances only every 15.6 ms or so, so a renewal right after a swap's write could keep its time), read them.
   A refresh token fingerprint other than the active row's is a login cc-rotate did not write: Claude Code's renewal of the active account's login, or a `/login` in the profile.
   When `.claude.json` names a different account than it did when last read, that is a `/login`, acted on at once: a pool account becomes active with that login (an `adopted_login` event), and an account outside the pool marks the profile foreign (a `foreign_login` event), after which nothing is stored from the profile until a swap or a re-login writes a pool account's login into it.
   Otherwise the profile alone cannot tell a `/login` from a renewal, since `.claude.json` keeps naming the account it named before the swaps since (F14): the login is stored only once Claude Code says whose it is (section 20.5), which the tick starts in the background.
   With usage checks off or stopped, it is stored as the active account's at once (`source = sync`), and a `/login` of the account `.claude.json` already names goes unnoticed.
   This keeps the store a few seconds behind Claude Code's own refreshes.
4. Evaluate triggers 1, 3 and 5 and spawn a detached swap if needed.
5. Forward the original stdin to the `statusline_downstream` command (if set) and print its output, prefixed with the active account label.

Budget: one `cc-rotate-ctl statusline` run without a downstream command (process start plus steps 1 to 4) completes in under 30 ms at the 95th percentile; the downstream command's own run time is added on top and is outside cc-rotate's control.

## 9. Usage reporting from the legacy profiles

The legacy profiles can run `cc-rotate-ctl statusline --observe` in front of their existing statusline.
Observe mode only records samples, attributed by `oauthAccount.accountUuid` from that profile's `.claude.json`, and tags them with the profile name.
It never touches credentials or triggers swaps.
This lets the dashboard show every account during a migration, and lets the scheduler avoid accounts the legacy profiles are draining.

### 9.1 Readings the other profiles already hold

Without any opt-in, cc-rotate reads the usage reading Claude Code cached in each of the user's other profiles (F16): every `.claude*` directory in the home directory except the rotation profile, with `~/.claude.json` for the default profile.

- A reading counts for a pool account when the profile's `oauthAccount.accountUuid` names it, the cache is stamped with the same id, and the profile's `oauthAccount.organizationUuid` is the account's organization; anything else is ignored.
  One person can belong to several organizations with one account id (a personal plan and a Team seat), and limits are per organization.
  A reading taken before a `/login` to another organization of the same person still carries the same stamp, so the organization is checked as the profile names it now; a profile switched between organizations can misattribute its last reading until it reads usage again.
- A profile whose status line is `cc-rotate-ctl statusline` without `--observe` is a rotation profile or a copy of one, whose login changes account (F14), and is skipped.
- It becomes a sample with the cache's `fetchedAtMs` as its time (at most now), tagged with the profile's folder name like observe mode, and only when it is newer than the account's latest sample.
- The latest sample's windows that a report cannot express (any name other than `five_hour`, `seven_day` and their model-family forms) are carried into the new sample while their reset has not passed, so a limit only the status line reports does not stop counting.
- Windows come from `limits[]` (older bodies: the `five_hour`, `seven_day`, `seven_day_opus` and `seven_day_sonnet` fields) and are named as the status line names them: `session` is `five_hour`, `weekly_all` is `seven_day`, and a row scoped to a model family is `five_hour_<family>` or `seven_day_<family>`.
  Rows of another kind, rows scoped to another product (`scope.surface` other than Claude Code) and rows scoped to a model family cc-rotate does not know are left out: the report covers the whole plan, unlike the status line, so a guess could park an account for days over a limit that does not apply, while a limit that does apply and was missed shows up in the status line on the first request (section 7.2).
- A config file is parsed again only after its modification time changed (`profile_usage_seen:<path>` in `meta`), and only its `oauthAccount` and `cachedUsageUtilization` are deserialized, so this stays cheap even though `.claude.json` files can be large.
  A profile signed in to an account outside the pool is not marked as read, so its reading is picked up once that account is added.
- It runs before a swap picks its target (section 6), in the background sync (the app every 5 s, and `cc-rotate-ctl status`), and in `cc-rotate-ctl next`, but not in the status line tick, whose time budget it does not fit.
- It only reads those files; it never reads their credentials.

## 10. Login flow

Used both for adding an account and for re-logging an account in `needs_login`.

1. Create `<data dir>/staging/<uuid>/`.
2. Spawn `claude auth login --claudeai --email <email>` with `CLAUDE_CONFIG_DIR` set to the staging directory, piping stdin, stdout and stderr.
   `--email` is omitted when adding a new account with no known email.
3. Parse the sign-in URL from stdout and show it, plus a paste-code field that writes to the child's stdin (F9).
   Claude Code opens the browser itself.
4. On exit code 0, read the staging credentials' `claudeAiOauth` (the file, or on macOS the staging directory's Keychain item) and the staging `.claude.json` `oauthAccount`.
5. For a re-login, refuse the import if `accountUuid` differs from the target account, and tell the user which email actually signed in.
6. Upsert the account and its credentials (`source = login`).
   A re-logged account goes to `parked`, or to `active` if the pool had no active account.
7. Delete the staging directory, including on failure, cancel, and the 10-minute timeout.

Rules:

- Every account in the pool gets its own fresh login.
  Tokens are never copied from the legacy profiles, because a shared refresh token would break whichever holder refreshes second.
- The browser signs in as whatever claude.ai account it is currently logged into.
  The UI states the expected email before opening and suggests a separate browser profile per account when the wrong one keeps signing in.
- `cc-rotate-ctl profiles` lists the user's other `.claude*` profiles in the home directory and the account each belongs to, read from its `.claude.json`.
  `cc-rotate-ctl login --from-profile <name>` starts a fresh login for that account with its email and label pre-filled, and refuses the import if a different account signs in.
  Discovery is read-only: it reads a profile's `.credentials.json` only to tell whether it is signed in, and never imports or writes it.

## 11. Dashboard app

`cc-rotate-app` is a Tauri 2 window plus a tray icon; closing the window hides it to the tray, and `cc-rotate-ctl dashboard` launches or focuses it.
It is single-instance, starts at login (toggle in the app), and exposes no network port: the UI talks to the Rust side only through Tauri commands and events.
The tray tooltip shows the active account, its 5-hour and weekly percentages (or that it has no weekly limit) and the next pick, refreshed on every store change and every 30 s; the tray menu offers Open, Swap now, and Quit.
Native notifications fire for `pool_exhausted`, `dead_login`, any account entering `needs_login`, and "<label> is ready again" when the pool stops being exhausted.
The watcher also starts the background usage checks (section 20.2).
The UI is TypeScript built with Vite, with uPlot for charts.
Light and dark themes follow the system.
UI copy uses no em dashes.

Views:

- **Pool header:** active account, the next pick with its reason, weekly headroom (summed weekly percentage remaining over usable accounts with a weekly limit) and the number without one, swaps in the last 24 hours, and a warning banner for `pool_exhausted` or any `needs_login`.
- **Accounts:** one row per account in the user's order, with a drag handle, label, plan ("Max 5x", "Max 20x", "Team", "Team 5x", "Pro", else the raw subscription type), email, state badge, 5-hour and weekly meters with reset countdowns ("No weekly limit" when it has none), model-scoped windows, and last-sample age.
  Dragging a handle reorders the accounts; a focused handle moves with the arrow keys (Home and End for first and last), and the account dialog has Move up and Move down.
  The drag uses pointer events rather than HTML drag and drop, which the platform webviews handle inconsistently.
  Row actions: Use now, Pause or Resume, Check usage, Sign in again, the weekly limit override (detect, has one, none), Remove.
  Each row says where its latest reading came from ("updated 5m ago", "updated 5m ago from work", "checked 5m ago").
- **Usage over time:** weekly percentage per account as lines over 7 days, a 5-hour percentage strip per account over 24 hours, and swap events as vertical markers labelled with the reason.
- **Events:** filterable log of swaps, skips, logins, syncs and errors.
- **Login:** the section 10 flow in a dialog with live status (waiting for browser, received, imported, failed).
- **Settings:** `doctor` results (section 12), the settings, Claude Code version, and the store path.

## 12. Errors, health and version safety

- Every failure path logs an `events` row and leaves `.credentials.json` either untouched or fully written, never partial.
- `cc-rotate-ctl doctor` checks:
  - the Claude Code version against the tested list,
  - that both lock paths resolve as expected,
  - that the profile's `statusLine` and `StopFailure` hook point at cc-rotate,
  - whether herdr is present (`HERDR_ENV` in a pane, or `herdr` on `PATH`) and the `SessionStart` hook is installed, warning only when herdr is present and would resume sessions with plain `claude` (section 19),
  - where Claude Code keeps the profile's login (file or Keychain item), failing if the Windows Credential Manager backend is on (section 18.2),
  - that no PowerShell profile still defines the old `cc-rotate` function,
  - that exactly one account is active, or that zero are and every account is `needs_login` or `paused`,
  - that `.credentials.json` matches the active account's `account_uuid` by fingerprint,
  - that every stored login decrypts, and where the key file is (warning if other users can read it),
  - whether usage checks are on, and every account whose last check failed, with the reason.
- On an untested Claude Code version, rotation still runs, the dashboard shows a warning, and the next manual verification uses the E2E suite below.
- Back up `.credentials.json` before the first swap of each day to `<data dir>/backups/credentials-<day>.ccr`, sealed as in section 5.1, keeping 7; `cc-rotate-ctl backup <file>` prints one.

## 14. Requirements

1. R1: A swap changes the account used by every running CLI session in the profile on that session's next API request, with no restart.
2. R2: No interleaving of a Claude Code token refresh and a swap leaves any account's stored refresh token retired.
3. R3: A swap writes only `claudeAiOauth`; `mcpOAuth` and every other key in `.credentials.json` parse to the same values before and after.
4. R4: Concurrent triggers from many sessions produce at most one swap per `--from` account.
5. R5: No automatic swap happens within `swap_cooldown_s` of the previous swap, except for `StopFailure`, a dead login, or a threshold on an account that arrived over its limit (section 7.2).
6. R6: When no account is eligible, nothing changes, and the dashboard shows a banner and (while the app runs) a native notification.
7. R7: The store and its backups never hold plaintext tokens on disk; they are sealed with authenticated encryption under a key file only the user can read (section 5.1).
8. R8: cc-rotate makes no network requests to Anthropic; the only requests it causes beyond the user's sessions and sign-ins are the usage checks Claude Code makes (section 20).
9. R9: The statusline path meets the section 8 latency budget.
10. R10: The login flow imports a working login without the user opening a terminal, and rejects a re-login that signed in as a different account.
11. R11: The legacy profiles' credentials are never read for import or written.
12. R12: Every swap, skip, login, sync and error is visible in the dashboard events view within 2 s.
13. R13: An account is never picked while a window that applies to the model in use is at or above its threshold, whatever the window's name.
14. R14: With `prefer_no_weekly_limit` on, no account with a weekly limit is picked while an eligible account without one exists.
15. R15: A switch back only goes to a strictly better ranked account, never sooner than `switch_back_dwell_s` after the active account became active, and never between accounts in the same place.
16. R16: Usage is attributed only to the account whose login produced it (F5, F14, F16, and the organization check in section 9.1); upgrading the store keeps every sample and the account order.
17. R17: A usage check never runs with a renewable copy of the active account's login, never deletes a login Claude Code may have renewed during it before storing it (including when the check dies or is killed), holds back an account whose login it cannot vouch for until a check settles it, never lets Claude Code run `/usage` as a prompt twice, and no automatic check of an account runs before the usage endpoint's `retry-after` ends.

## 17. Decisions

1. Both swap thresholds default to 98%.
2. Every account joins the pool through a fresh login made inside cc-rotate (section 10).
   E2E tests E1 to E7 need two logged-in accounts; E8 needs one account genuinely at its limit.
3. There is no reserve concept in v1: every `parked` account is eligible, and `paused` is how a user holds one back.
4. The project is open source under the MIT license; no code or doc may assume a particular user, path, or account count.
5. Windows and Linux are supported; the store's encryption is the same on every platform (section 5.1).
   Platform-specific code (process flags and detaching, the launcher's signal handling, command quoting, the DPAPI conversion) sits behind `cfg(windows)` and `cfg(unix)`.
   CI builds, lints and tests the whole workspace, including the desktop app, on Windows, Linux and macOS.
6. Limits are modelled generically (section 7.1), because cc-rotate is not built for one set of plans.
   Accounts without a weekly limit are used first, then the user's order, then the most room; a better ranked account is switched back to once usable, after a dwell.
   A switch back also overrides an account picked by hand; pausing is how a user keeps an account out.
7. Whether an account has a weekly limit is detected from its usage, with a per-account override, never assumed from its plan: some Team seats report no weekly limit although plans normally have one.

## 18. Credential storage per platform

Claude Code 2.1.310 picks its credential storage per platform build, and cc-rotate mirrors it in `credstore`:

| Platform | Where Claude Code keeps the credentials document |
|---|---|
| Windows | `<CLAUDE_CONFIG_DIR>/.credentials.json`, unless the Credential Manager backend is on (below) |
| Linux | `<CLAUDE_CONFIG_DIR>/.credentials.json` only |
| macOS | A login Keychain item, with `.credentials.json` as the fallback |

### 18.1 macOS Keychain

- The item is a generic password with service `Claude Code-credentials-<h>`, where `<h>` is the first 8 hex digits of SHA-256 over the NFC-normalized `CLAUDE_CONFIG_DIR` string exactly as given (no suffix when the variable is unset), and account `$USER` (else the OS user name; `claude-code-user` when it has characters outside `[A-Za-z0-9._-]`).
  The `cc-rotate` launcher sets the variable to the recorded profile path, so cc-rotate and Claude Code compute the same name.
- The item holds the same JSON document as the file.
  Claude Code reads it with `security find-generic-password -a <user> -w -s <service>` and writes it with `security -i`, feeding `add-generic-password -U -a "<user>" -s "<service>" -X "<hex of JSON>"` on stdin (on the command line instead when that line is over 4032 bytes).
  cc-rotate runs the same commands through `/usr/bin/security`, so items Claude Code created never prompt, and confirms each write by reading the item back.
- Reads take the Keychain item when there is one, else the file; exit code 44 (no item) and 36 (Keychain locked or no GUI session, for example over SSH) fall back to the file, as in Claude Code.
- Writes go where the document is now. A profile with no credentials anywhere gets the file, which Claude Code reads as its fallback and moves into the Keychain on its own next write.
- Claude Code caches a Keychain read for 30 s and has no mtime to compare, so a swap reaches running sessions within about 30 s rather than on the next request (R1 is relaxed to that on macOS).
  cc-rotate's statusline detects changes with a fingerprint of the item, as it does for the file.
- The refresh locks are the same directories as on the other platforms.
- A login made in a staging directory lands in that directory's Keychain item; the staging cleanup deletes the item along with the directory, on success, failure, cancel and timeout.
- To verify on a Mac: the `credstore` unit tests (service names against values computed with Claude Code's own expression), then E1 to E7 with the 30 s allowance.

### 18.2 Windows Credential Manager

Claude Code 2.1.310 on Windows also contains a `credential-manager` backend (with the file as fallback).
It is used when `CLAUDE_CODE_FORCE_WINDOWS_CREDMAN=1`, or when the server-side flag `tengu_windows_credman` is cached as on: `cachedGrowthBookFeatures.tengu_windows_credman` in `<CLAUDE_CONFIG_DIR>/.config.json` when that file has content, else in `<CLAUDE_CONFIG_DIR>/.claude.json`.
With it on, swaps written to the file would no longer reach running sessions, so `doctor` fails the "Claude Code login storage" check.

## 19. herdr session resume

[herdr](https://github.com/herdrdev/herdr) is a terminal workspace manager for coding agents.
When its server restarts it restores each pane and, with `resume_agents_on_restore` (on by default), resumes the agent session that ran there.
For Claude Code its built-in command is `claude --resume <id>`, which runs on the default profile, so a cc-rotate session would come back outside the pool.
herdr 0.9.2 and newer let an integration report its own resume command, and a reported command wins over the built-in one on restore.
These behaviors were read from herdr's source at 0.9.4 and confirmed against an isolated herdr instance.

| # | herdr behavior | Why it matters |
|---|---|---|
| H1 | `herdr pane report-agent-session <pane> --source <id> --agent <label> [--seq <n>] -- <argv...>` records a resume command for the pane. `--source` is free-form except for the reserved `herdr:` prefix, and `--seq` orders reports per source: an older one exits 0 but is ignored. | cc-rotate reports under `cc-rotate` with the hook's time in ms as `--seq`, so a late report never replaces a newer session. |
| H2 | The command is rejected (`invalid_resume_argv`) unless the first element is a bare name (`[A-Za-z0-9_.-]`, not starting with `-`), no element has an apostrophe or a control character, and there are at most 64 elements and 8 KiB. | The command is exactly `cc-rotate --resume <session id>`, and a session id that is not a plain token is refused before reporting. |
| H3 | Until herdr has seen a `claude` process in the pane (any descendant of the pane's shell), the report fails with `resume_not_accepted` (CLI exit 1, JSON error on stderr). A rejected report does not consume its `--seq`. | The report is retried every 500 ms for up to 15 s with the same `--seq`; in practice herdr accepts it within about half a second. |
| H4 | On restore, herdr starts the pane's default shell and types the command and Enter, quoting arguments POSIX-style. | `cc-rotate` must be on `PATH`; plain tokens type the same in every shell. |
| H5 | When the `claude` process exits, herdr clears the reported command and its own saved session for the pane. | No `SessionEnd` hook is needed. `release-agent` is never called (it would also fire on `/clear` and race the new report), and neither is `report-agent`, which would take over the pane's status display. |
| H6 | Panes get `HERDR_ENV=1`, `HERDR_PANE_ID`, `HERDR_SOCKET_PATH` and `HERDR_BIN_PATH` (the herdr executable), which hooks inherit. herdr's own Claude Code hook (`herdr-agent-state`, copied into the rotation profile by setup with the rest of the hooks) reports only the session id, under `herdr:claude`. | The hook finds the pane and the right server from the environment, and the two reports do not interfere. |

The flow:

1. `setup` adds a `SessionStart` group with matcher `^(startup|resume|clear|compact|fork)$` running `cc-rotate-ctl hook session-start` with a 10 s timeout (section 4.3).
2. The hook exits at once unless `HERDR_ENV=1` and `HERDR_PANE_ID` are set.
   It skips subagents, which carry a non-empty `agent_id` (`agent_type` alone is also set for a main session started with `claude --agent`), takes `session_id`, and starts `cc-rotate-ctl herdr-report --seq <now ms> -- <pane> <session id>` in the background with the same detaching as the background swap.
   The detached process keeps none of the hook's standard handles, so Claude Code's startup never waits for it.
   The hook prints nothing, since Claude Code adds a `SessionStart` hook's output to the session's context.
3. `herdr-report` runs `$HERDR_BIN_PATH` (else `herdr` on `PATH`) with `pane report-agent-session <pane> --source cc-rotate --agent claude --seq <n> -- cc-rotate --resume <session id>`, retrying `resume_not_accepted` as in H3.
4. Every failure goes to the log; none reaches Claude Code.

Sessions started before the hook was installed keep herdr's built-in command until they start again in a covered way (a new start, `--resume`, `/clear`, or compaction).
Testing: unit tests cover the hook input, the command against H2, and the settings merge; an integration test drives the hook and the report against a fake `herdr` that refuses twice; the end-to-end check restarts an isolated herdr server and confirms the restored pane runs `cc-rotate --resume <id>`, and that quitting the session clears the report.

## 20. Usage checks

The status line only reads the account in use, and the other profiles' readings (section 9.1) only exist for accounts used there.
A usage check reads an account with Claude Code's own `/usage` (F17).

### 20.1 One check

1. Take the account's lock, `<data dir>/locks/account-<id>.lock` (proper-lockfile semantics like the swap lock), without waiting for an automatic check and up to `lock_timeout_ms` for one the user asked for.
   A swap takes the same lock before it reads the account's stored login to write it into the profile (section 6), and so does a re-login of an existing account (waiting up to `lock_timeout_ms` plus the 60 s a check may run), so no two of them use one login at once.
2. Recover what an earlier check that died left behind (20.3), then re-read the account under the lock: an active account (its status line reads it), an account that needs a login, and a paused one (unless the user asked) are not checked, and neither is an account whose stored login is the one the rotation profile holds (a swap that stopped half way can leave it there): Claude Code renewing it in the check would sign the profile's sessions out.
3. Create a scratch profile `<data dir>/staging/check-<id>-<start ms>-<uuid>/` holding the stored `claudeAiOauth` in `.credentials.json`, and in `start.fp` the fingerprint of that login.
   No identity is given: Claude Code fetches the account's profile itself and stamps the reading with the account the login really belongs to.
   When the account is held back (20.3), the login's `expiresAt` is set to 0, so Claude Code renews it and the check settles whether it still works.
4. Run `claude -p /usage --output-format json --debug-file <scratch>/debug.log` with `CLAUDE_CONFIG_DIR` set to the scratch profile, the scratch profile as the working folder, every `ANTHROPIC_*`, `CLAUDE_CODE_*`, `CLAUDECODE*` and `HERDR_*` variable removed except how Claude Code reaches the network and finds Git Bash (`CLAUDE_CODE_GIT_BASH_PATH`, `CLAUDE_CODE_CERT_STORE`, `CLAUDE_CODE_CLIENT_CERT`, `CLAUDE_CODE_CLIENT_KEY`, `CLAUDE_CODE_CLIENT_KEY_PASSPHRASE`, `CLAUDE_CODE_HTTP_PROXY`, `CLAUDE_CODE_HTTPS_PROXY`), `DISABLE_AUTOUPDATER=1`, and no console window on Windows.
   Its output goes to files in the scratch profile (no pipes a stray process could hold open), its process id to `claude.pid`, and it runs as a process tree (a job object that kills the tree when closed on Windows, which also happens if cc-rotate dies; its own process group on Unix) that is killed as a whole after 60 s (30 s before a swap).
5. Read the scratch profile: its login (the file, or on macOS the scratch profile's Keychain item), its `cachedUsageUtilization`, the result on stdout and the debug log.
   When the login cannot be read, nothing is decided: the scratch profile stays for 20.3, and the account is held back.
6. When the result shows a model turn (`num_turns` above 0, a `total_cost_usd` above 0, or output tokens), Claude Code ran the text as a prompt, a model request on the account's quota: checks stop (`usage_checks_blocked` in `meta`, an `error` event) until the user sets `usage_checks` again. An error result is only a failed check.
7. In one transaction:
   - a login whose refresh token changed is stored (`source = check`, a `sync` event with reason `usage_check`), and a blanked one (F8) marks the account `needs_login` with a `dead_login` event;
   - a reading fetched during this check and stamped with the account's id becomes a sample (`profile = check`), named as in section 9.1, with the previous sample's windows a report cannot express carried over, and its reset times become the account's own (section 8);
   - a reading stamped with another account's id means the stored login belongs to that account: the account is marked `needs_login` with an `error` event;
   - the account's check state (`usage_check:<id>` in `meta`: last attempt, last reading, `not_before`, `held_back`, the last failure for people) is updated;
   - when the account's stored login or state changed during the check (a `/login` in the profile adopted it), the check's verdict on the old login (a renewal, a rejection, another account) is dropped; its reading still counts.
8. Only after the transaction commits, delete the scratch profile and its Keychain item.

A 429 (the debug log's `429 remembered ... not asking again for <n>s` from the usage fetch, else 5 minutes) sets `not_before` to when the endpoint will answer again, between 1 minute and 1 hour; any other failure sets it `usage_check_interval_s` ahead.
On Windows, checks do not run while the rotation profile uses the Credential Manager backend (section 18.2), and a check that finds Claude Code switched to it stops checks and holds the account back, since a login it renewed there is invisible to cc-rotate.

### 20.2 When checks run

- Before a swap (section 6, step 3), for a pick whose latest reading is older than `usage_check_max_age_s`, unless the request names its target.
  This keeps a swap from landing on an account that was used up where cc-rotate could not see it, and gives the account's own reset times for section 8.
- In the app, every minute, at most one at a time: first a held-back account not tried in the last 5 minutes, then the first account in pick order that is parked, has no reading and no check attempt newer than `usage_check_interval_s`, and whose `not_before` has passed (`usage_check::next_due`).
  An account a check skipped for its own reasons (its lock busy, a check of it still running) counts as tried, so the others are not starved.
- When the user asks: `cc-rotate-ctl check [<account>...]`, or **Check usage** in the app, which ignore `not_before` and also check paused accounts; with `usage_checks false` they still run, the automatic ones do not.
- `cc-rotate-ctl check` and the app at start first settle every scratch profile left behind (`usage_check::sweep`).

### 20.3 A check that dies or is interrupted

Claude Code may have renewed the login in the scratch profile, retiring the stored refresh token, when the check dies before step 7 commits or is killed at its time limit, and the renewal may be lost with it (killed before it wrote the new login).

- A scratch profile left behind always means the check did not store its outcome. The next holder of the account's lock (a check or a swap of that account, or the sweep at app start) settles it:
  - `start.fp` is written before the login: without it, or with a fingerprint other than the stored login's (a re-login since), the leftover is stale and deleted unread;
  - a renewed login in it is stored, and a blanked one marks the account `needs_login`;
  - anything else (the login unchanged, none left) leaves the doubt, and the account is held back;
  - a login that cannot be read is kept, with the account held back and counting as busy, for an hour in case it becomes readable (a locked Keychain, a file another program holds), then given up the same way.
- A check records its Claude Code's process id with its start time (`claude.pid`); while that process runs (on Unix, while any process of its process group runs, since what it started outlives it), its scratch profile is left alone and the account counts as busy (a swap passes over it). A reused process id has another start time and does not count.
- After a check, a timeout, an error while waiting for Claude Code (which then is killed), or no login left at all hold the account back too.
- A held-back account is not picked, not swapped to by hand, and its next check (5 minutes after a failure, respecting the usage endpoint's wait) makes Claude Code renew (20.1, step 3), which settles it either way.
- A fresh login of the account clears its check state and deletes its leftovers; removing an account takes its lock and deletes its scratch profiles and check state.

### 20.4 Confirming the account in use

A threshold swap whose trigger is a status line reading with a window over its threshold whose reset time is not known to be the account's own, or is another account's too (section 8), first reads the account in use's usage (`usage_check::confirm_active`), within the swap's 25 s budget for checks.
It uses a copy of the profile's login with the refresh token removed, so Claude Code cannot renew (and so retire) the login the profile's sessions use; when the access token expires within two minutes, there is no confirmation.
The scratch profile is `<data dir>/staging/confirm-<uuid>/`, never recovered and deleted afterwards (and by the sweep).
A reading stamped with the account becomes its sample (`profile = check`) and its reset times its own; when the account is below its thresholds by it, the swap is skipped.
When the confirmation cannot be made (rate limited, no access token, an error), the swap goes ahead as the reading says, as before.

The status line also asks for a confirmation in the background (`cc-rotate-ctl confirm-active`) when readings it drops as another account's are at a limit while no reading of the account in use arrived for 10 minutes, so wrong reset times cannot hide a used-up account: the first such reading since the account became active asks at once, copy or not (at a limit, a genuine reading can repeat another account's exactly, both at 100% with the same reset time); after that, a reading asks only when it is not an exact copy of another account's latest (a session idle since an earlier swap repeats it for as long as it idles) and no reading of the account in use came for 10 minutes, at most every 10 minutes. One of the sessions ticking at once asks.

### 20.5 Identifying a changed login

A login that changed in the profile without cc-rotate writing it, and that `.claude.json` does not reveal as a `/login` (section 8, step 3), is identified before it is stored (`swap::identify_changed_login`).
Claude Code is asked whose it is the way a stopped swap's login is (section 6): with a copy whose refresh token is removed, in a scratch profile, matching the account id or else the email, and the organization where both are known.

- The active account's login (a renewal) is stored as its login.
- Another pool account's login (a `/login` of an account `.claude.json` already named, from before a swap) makes that account active with it; the account that was active keeps its own stored login.
- Any other account's login marks the profile foreign, so it is never stored.

It runs with the swap lock, at most once a minute: started in the background by a status line tick (`cc-rotate-ctl settle-login`), by the app on its own thread, or by `cc-rotate-ctl status`.
A swap identifies first, so it never stores another account's login as the outgoing account's; when the profile's login changed again, unseen, by the time it holds Claude Code's locks (it may have checked accounts meanwhile), it skips, and the next request identifies that login first.
A re-login of the active account stores its fresh login again under the swap lock as it writes it into the profile, so an identification running meanwhile cannot leave the store with the profile's previous login.
While Claude Code cannot say (the access token expires within two minutes, Claude Code fails, no network), the login is not stored and no swap runs.
That lasts at most 10 minutes: then the login is stored as the active account's, as before logins were identified, and an `error` event says so, so a Claude Code that cannot identify logins never stops the rotation; `doctor` warns from two minutes on.
It is a routine run of Claude Code like a check, so it follows the `usage_checks` setting and stops with checks (20.2); on macOS it also needs a Keychain that can be used. Otherwise (checks off or stopped, or the Keychain locked) a changed login is stored as the active account's at once, as before.
